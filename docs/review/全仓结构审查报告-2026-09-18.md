## 0. 结论摘要

| 维度 | 结论 |
|---|---|
| 项目性质 | 桌面级制造物理 AI（Tauri + Vue3 + FastAPI 单体 monorepo），非 Web SaaS |
| 代码规模 | Python 5,698 文件（后端 app 1,097 文件 / 26.9 万行）；前端 209 `.vue` + 190 `.ts` / 7.1 万行 |
| 架构清晰度 | **中上**。三层装配（main → router_registry → 域注册）职责分明，装配层已做拆分 |
| 工程质量 | **中等偏上，但呈"文档领先于实现"**。测试 7,923 通过 / 0 失败，但覆盖率门禁仅 24% |
| 最大结构性问题 | **能力接线缺口 > 能力缺失**：多个上千行、测试完备的模块长期无 API / 无页面挂载 |
| 最需警惕的硬伤 | Rust 计算内核从未构建接入；覆盖率门禁与 `AGENTS.md`「≥80%」约定严重脱节；文档数字多处失真 |

**一句话**：这是一个功能面已相当完整、自审文档质量罕见地高、但「宣称—资产」之间存在多处系统性偏差的项目。它的主要风险不在"没做出来"，而在"做出来了但没接上"和"说了但没做"。

## 1. 项目主要目标与功能

### 1.1 定位

灵境制造是**装在工厂自己电脑里的制造物理 AI**（Desktop Physical AI for Machining），面向中小型制造企业的 CAM 编程痛点。

主推定位（`docs/产品叙事与战略对标-2026-09.md` §1.3）：

> **图纸进，代码出——每一行 G 代码都经过物理校验才上机，每一份数据都留在你自己的电脑里。**

### 1.2 三大产品支柱（每根支柱均有代码资产兜底）

| 支柱 | 口号 | 背后资产 | 状态 |
|---|---|---|---|
| ① 敢上机 | "AI 说的不算，物理说了算" | `cam_validation/voxel_validator.py` + DNC 下发硬闸（403 / 错误码 8013）+ 颤振 LNN 预测 | 已落地 |
| ② 不泄密 | "你的工艺秘密不需要上别人的云" | 9+ LLM 可插拔且全本地可用、SQLite/ChromaDB 全本地、MCP 网关 fail-closed 鉴权 | 已落地 |
| ③ 越用越懂你 | "第三个月，它已见过你车间两千次真实反馈" | `plugins/data_flywheel`、cutting_experience 经验库、`pipelines/feedback_loop` | 骨架已建 / 数据冷启动 |

### 1.3 核心业务流程（阶段 1–7）

```
阶段1 图纸/图像 → 阶段2 特征提取 → 阶段3 参数化几何
  → 阶段4 切削参数 → 阶段5 颤振预测 → 阶段6 G代码生成+后处理
  → 阶段7 CAM 二次校验（内部预校验 + CAM软件 + 体素仿真 + 运动学 K001-K009）
  → 工程师审核确认 → DNC 下发硬闸
```

**关键设计**：阶段 7 产物终止于「CAM 校验报告 JSON」，系统**绝不直接接口 CNC 控制器**，CAM 软件调用走 subprocess。系统定位是「工程师助手」而非「全自动 CAM 校验器」——这条纪律在 `cam_validation/pipeline.py:47-55` 以「工业硬约束」形式写死在代码注释里。

## 5. 模块之间的调用与协作

### 5.1 进程协作（桌面模式）

```
Tauri(Rust) 启动
  → 解析 python.exe 路径（desktop_runtime → LINGJING_PYTHON_PATH → 系统探测）
  → 端口探测：8765 起 +0..+20，全占用则 bind(0) 随机
  → spawn sidecar（注入 SERVER_PORT / LNN_LOG_DIR / LNN_STATE_FILE）
  → 轮询 GET /api/health/ping（90 次 × 500ms = 45s 超时）
  → 就绪后关闭 splashscreen，延迟 500ms 建主窗口
  → 退出：先 POST /api/v1/admin/shutdown（超时 2s）→ 成功则等 5s → kill
```

**端口自适应是这里的关键设计**：Rust 端 8765 被占用会自动漂移，前端 `utils/http.ts:105` 通过 `setBackendPort(port)` 动态注入 baseURL，绝不硬编码。

### 5.2 请求链路

```
Vue 组件 → Pinia store → api/*.ts → utils/http.ts (axios)
  → Vite proxy(/api, /agents) 或 Tauri 下 http://127.0.0.1:{port}
    → register_middleware_stack（6 层）
      → api/routers 域路由 → api/v1 路由处理
        → services/ 业务层 → 域模块（dxf / planning / simulation ...）
          → database/ (SQLite) · rag/ (ChromaDB) · ai/ (ONNX/LLM)
```

SSE 用原生 `EventSource`（不走 axios baseURL），封装在 `composables/sseConnection.ts`，带 epoch 竞态防护 + 指数退避重连（baseDelay 1s / maxDelay 30s / maxRetries 10）。

### 5.3 外部 Agent 链路

```
外部 Agent ──MCP(stdio/SSE)──▶ mcp_server ──HTTP + Bearer──▶ 后端 /api/agent/v1/*
```
`mcp_server` 26 个工具分 7 组（LNN 6 / G代码任务 3 / 设备 7 / 工厂 4 / CAM 4 / DXF 1 / 工艺规划 1），每组独立开关。出站用 `httpx.AsyncClient(trust_env=False)` 防代理劫持，写操作附 `Idempotency-Key`。

## 6. 值得注意的核心逻辑

### 6.1 DNC 下发硬闸（全项目最硬的设计）

`app/dnc/nc_gate.py` 是「敢上机」叙事的物理落点。下发前要求目标程序能追溯到一个满足**全部**条件的状态 7 校验任务：

1. `source_gcode_file_path` 与待发送程序同文件（路径归一化，Windows 忽略大小写）
2. 状态 = `SUCCEEDED`（工程师已审核确认）
3. `voxel_check_passed is True` ← **`None` 按未通过处理**（闭环上线前的历史任务）
4. `kinematics_check_passed is True` ← 同样 `None` 按未通过处理

三个设计细节值得学习：

- **fail-closed 的逃生阀**：`LNN_DNC_ALLOW_UNVALIDATED_NC=1` 可放行，但每次下发打 warning 留痕
- **延迟导入**：`nc_gate.py:69` 在函数内 import cam_validation，避免 dnc 模块加载即拉起 `cam_validation → simulation` 依赖链
- **导出侧不设闸**：阶段 6 导出产物是阶段 7 的输入，在导出处拦截会造成流水线死锁——这个取舍写得很清楚

配套的程序级运动学校验 `simulation/kinematics/validator.py` 定义 **K001–K009** 判据（K001 轴行程超限 / K002 主轴未运转 / K006 快移扎刀 / K009 无 M30 为 warning，其余 error）。

### 6.2 三层条件降级

| 场景 | 降级路径 |
|---|---|
| LLM provider 不可用 | 软依赖 + 规则引擎回退（`_OLLAMA_AVAILABLE` 等 flag 控制路由注册） |
| Rust 体素内核缺失 | `rust_engine.py:79-101` 导入期探测失败 → `RUST_ENGINE_AVAILABLE=False` → 纯 Python 逐函数回退 |
| Redis 不可达 | `get_redis()` 内部降级到内存缓存 |

### 6.3 启动与关闭的容错哲学

`main.py` 的 startup 事件里**每一步依赖初始化都包了 try/except**（init_db / get_redis / AsyncTaskManager / 插件系统 / 演化注册 / 状态持久化），失败仅记 ERROR 不阻断启动。注释解释了理由：FastAPI startup 失败不会触发 shutdown_event，会导致 ring_log 文件句柄泄漏（Windows 下锁定日志文件）。

关闭顺序严格分层（P2-3 优化）：**调度层（HeartbeatScheduler）→ 执行层（AsyncTaskManager）→ 业务模块（Budget/Cost/Rule/Goal/Audit）→ 外部依赖（Redis/HTTP）→ 持久化（DB/ChromaDB）→ 日志**。这是为 Windows 文件句柄锁定问题专门设计的。

### 6.4 其他值得肯定的细节

- **鉴权存储**：`stores/auth.ts` 用 `sessionStorage` 而非 localStorage，刻意降低 XSS 窃取面；`normalizeRole()` 对未知 role 降级为 `viewer` 防提权
- **响应拦截器**：GET 请求自动重试（指数退避 + 抖动，可重试 408/429/500/502/503/504），401 自动登出
- **契约层**：前端 `src/contracts/` 13 个文件明确对应后端 `app/contracts/__init__.py`，五大契约（Task/Workflow、Dataset/Lineage、Plugin/ExtensionPoint、ConfigSpec、Observability）
- **CORS 启动期强制校验**：通配符 + credentials 直接 `sys.exit(1)`，绝不带病上线
- **叙事纪律写进文档**：`docs/产品叙事与战略对标-2026-09.md` §1.6 明列 5 条红线（不说"无人化"、不承诺"支持任意机床"、叙事不跑在能力前面…），§1.7 提供「叙事↔资产对照表」作为维护工具

## 7. 潜在问题清单

### P0 — 需要尽快处置

**P0-1. Rust 计算内核从未构建、从未接入运行时**

`PROJECT_OVERVIEW.md` 声称「性能关键仿真调用 Rust compute-core (PyO3)」，但实测：

- `rust/compute/target/` **不存在**（无构建痕迹）
- 全仓无 `_native*.pyd` / `_native*.so`
- `engineering/python/_wheels/` 无 compute wheel；`requirements.txt` 无 compute 条目
- `desktop_runtime/runtime/Lib/site-packages/` 无 `compute` 包

结论：`RUST_ENGINE_AVAILABLE` 在**开发与打包分发中恒为 False**，所有体素切削静默走纯 Python `_apply_tool_mask_batch`。Rust 代码本身质量不低（`cutting.rs` 10 测试 / `voxel_grid.rs` 7 / `tool.rs` 9 + bench），问题是**构建与依赖链路完全没打通**。
→ 建议：要么在 CI 加 maturin 构建步骤并写入 requirements，要么从对外叙事中移除该宣称（叙事纪律第 3 条明确要求「叙事不跑在能力前面」）。

**P0-2. 覆盖率门禁与开发约定严重脱节**

`AGENTS.md` 写「覆盖率 ≥80% 才可合并」，实际：

| 位置 | 阈值 | 实测 |
|---|---|---|
| `.coveragerc` / CI unit·integration·full | **24%** | 历史 24.45% |
| CI contracts-tests | 65% | 68.00% |
| `vitest.config.ts` 前端 | 34/75/36/34 | — |

`.coveragerc` 注释承认是「由 65% 下调至 24% 以反映实测」——即**阈值追着实际跑，而非实际追着阈值**。前端 34% 同理。
→ 建议：要么把 `AGENTS.md` 的 80% 改为分期目标（如「新模块 ≥80%，存量棘轮抬升」），要么启动棘轮机制。当前的写法会让任何一次评审变成口径之争。

### P1 — 应当排期修复

**P1-4. CI 门禁存在形同虚设项**

- `ci.yml` test-summary 读 artifact 路径 `unit-test-results-py310`，但 matrix 是 3.11/3.12 → **永远匹配不到，覆盖率摘要静默跳过**
- `pr.yml` test-summary 硬编码「阈值 65%」，与实际 24% 矛盾（与 `ci.yml` 同段自相矛盾）
- **commitlint 无 CI 门禁**，仅本地 husky，提交规范可在 CI 侧绕过
- **flake8 有 pre-commit 无 CI**；**mypy 全仓零配置**
- `dependency-scan.yml` 两个 job 均 `|| true`，仅建基线不阻断
- `release.yml` 的 full-test-suite 可被 `inputs.skip_tests` 跳过，而 build-release 依赖它 → 手动发版可绕过测试门禁
- `ci.yml` 的 performance-benchmarks job 长期失败（发版报告 §3 明确「未处置」），却被 test-summary 依赖

**P1-5. 根 lint-staged 的 cargo fmt 会误拦提交**

发版报告称已修为 `--manifest-path src-tauri/Cargo.toml`，但该修复只落在 `engineering/package.json` 的内嵌 lint-staged 段。**husky 从仓库根运行，实际读根 `lint-staged.config.cjs`，其中仍是 `cargo fmt --`，而根目录已无 `src-tauri/`** → 含 `.rs` 的提交仍会被误拦。

**P1-6. 前端遗留两套路由实现**

`router/index.ts`（History 模式，生产使用）与 `router/createAppRouter.ts`（Hash 模式工厂，仅测试引用）。后者是死代码，且会造成"到底用哪个"的认知负担。

**P1-7. 桌面壳缺单实例锁与崩溃重启**

- 无 `tauri-plugin-single-instance` → 可重复启动产生多个 sidecar，SQLite 并发写有风险
- `sidecar.rs:351` 检测到崩溃仅置 `Crashed`，**不触发自动重启**；`restart()` 只由用户 IPC 或 `auto_fix_health` 调用
- 优雅关闭在 graceful 失败时**不等待直接 kill**（`sidecar.rs:526-535`）

**P1-8. `lib.rs` 残留硬编码调试代码**

`lib.rs:317-379` 注入了一段诊断 JS，其中 `fetch('http://127.0.0.1:8765/...')` **端口写死**，与「端口自适应」设计直接冲突。prod 构建前应清理。

**P1-9. 能力接线缺口（文档已自认）**

`docs/产品叙事与战略对标-2026-09.md` §4.1 的定性很准确——「仓库最大的问题已经不是缺能力，而是能力与产品、叙事之间的接线缺口」。2026-09 已修掉大部分（`unified_embedding` 有 API 出口、`dreaming` 有七端点、`world_model` 进入主叙事），剩余：

- `dreaming`（~8,000 行全仓最大模块）测试仍只覆盖一角
- `ai/lnn/router`（384 行任务路由）**无独立测试**
- `xmaker` 藏在 `dxf/api` 后面，无独立路由

### P2 — 卫生问题

**P2-10. 巨型文件**：`agent/orchestrator.py` 1,535 行 / 70KB 仍为全仓最大（重构计划已列但未拆）；`services/rl_agent_service.py` 1,035 行、`workflow/runner.py` 943 行等 Top 20 均超 800 行。

## 8. 建议的处置优先级

| 优先级 | 事项 | 理由 |
|---|---|---|
| 1 | Rust 内核：接入 CI 构建 或 从叙事中移除 | 叙事纪律第 3 条的红线问题 |
| 2 | 覆盖率口径统一（`AGENTS.md` 80% vs 实际 24%） | 任何一次评审都会变成口径之争 |
| 3 | 文档数字自动化校验脚本 | 答辩/对外场景的硬伤，且易复发 |
| 4 | CI 门禁修复（artifact 路径、commitlint、release skip_tests） | 门禁失效等于无门禁 |
| 5 | 单实例锁 + 崩溃重启 | 直接影响桌面产品体验与数据一致性 |
| 6 | 清理 `lib.rs` 调试注入 + `createAppRouter.ts` 死代码 | 低成本高收益 |
