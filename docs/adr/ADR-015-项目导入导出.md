# ADR-015: 项目导入导出（`.lomo` 包格式）

**日期**: 2026-07-14
**状态**: 已接受
**决策者**: 灵境制造团队
**关联**: ADR-005（核心架构契约）、ADR-011（项目级 Git 同步）、ADR-012（资源卡片）

---

## 背景

阶段 6 的目标是"生态内容飞轮"。p6-2 已实现项目级 Git 同步（在线协作场景），
p6-3 已实现模型/数据集卡片（资源展示场景），但在真实车间与离线协作场景中，
仍存在以下缺口：

### 当前现状

1. **Git 同步依赖远端仓库**：ADR-011 的 `push` / `pull` / `clone` 都需要可访问的
   Git 远端（GitHub / Gitea / 内网 GitLab）。但车间网络通常隔离，且部分用户没有
   Git 远端账号，无法通过 Git 完成项目跨机器迁移。
2. **资源内容未随项目导出**：ADR-011 的 `ResourceRef` 仅记录 `content_hash`，不打包
   资源内容。如果目标机器没有原始数据集/模型文件，clone 后项目"形同空壳"，无法
   直接运行工作流。
3. **模板市场需要归档格式**：ADR-010 工作流模板市场已支持模板上传/下载，但模板
   仅含 `WorkflowSpec`，不含数据集与模型。完整项目（数据集 + 模型 + 工作流 + 配置）
   的发布需要一个自包含的归档格式。
4. **备份场景**：用户希望将整个项目导出为单一文件备份，避免散落在多个目录的
   `datasets/` / `models/` / `output/workflows/` 难以一次性归档。

### p6-4 目标

- **离线归档**：将项目及其所有引用资源打包为单一 `.lomo` 文件，不依赖 Git 远端
- **内容自包含**：与 ADR-011 的"引用同步"互补，本 ADR 提供"内容同步"——包内
  包含数据集内容、模型文件、工作流 spec、配置 YAML，导入后即可运行
- **跨机器迁移**：用户在 A 机器导出 `.lomo`，拷贝到 B 机器导入，项目立即可用
- **模板市场扩展**：未来模板市场可支持"完整项目模板"（含示例数据集与预训练模型），
  本 ADR 提供归档格式基础
- **工程友好**：支持流式导出（避免内存爆炸）、校验和（防止传输损坏）、可选内容
  （仅元数据 / 含内容 / 仅小文件），适配车间大文件场景

## 决策

采用"**ZIP 归档 + JSON 清单 + 内容寻址 + 冲突策略**"方案，定义 `.lomo` 包格式，
**不修改现有 ProjectSyncService / ResourceCardService**，新建独立的
`ProjectPackageService` 处理导入导出：

### 1. `.lomo` 包文件结构

`.lomo` 文件本质是 ZIP 归档（扩展名 `.lomo`），内部结构如下：

```
project.lomo (ZIP)
├── manifest.json                  # 包清单（格式版本 + 项目元数据 + 资源清单 + 校验和）
├── README.md                      # 项目 README（可选，来自 manifest.description 渲染）
├── .lomo-project.yaml             # Git 同步清单投影（与 ADR-011 对齐，导入后可继续 Git 同步）
├── datasets/                      # 数据集内容（按 dataset_id 寻址）
│   └── <dataset_id>/
│       ├── meta.json              # Dataset 元数据（schema/owner/status/description）
│       ├── readmes/
│       │   ├── dataset_level.md   # 数据集级 README（version=null）
│       │   └── <version>.md       # 版本级 README（如 1.0.0.md）
│       └── versions/
│           └── <version>/
│               ├── meta.json      # DatasetVersion 元数据（row_count/size_bytes/storage_uri/lineage_record_id）
│               └── data.<ext>     # 数据内容（parquet/csv/json 之一，按原 storage_uri 后缀）
├── models/                        # 模型产物（按 model_id 寻址）
│   └── <model_id>/
│       ├── meta.json              # ModelArtifact 元数据（model_uri/type/version/framework/metrics/tags/status）
│       ├── readme.md              # 模型 README（model_artifacts.readme_md）
│       └── files/                 # 模型文件（按 storage_uri 抽取，保留原文件名）
│           └── <filename>         # 如 model.pt / model.onnx / model.pkl
├── workflows/                     # 工作流定义
│   └── <run_id>/
│       └── spec.json              # WorkflowSpec（DAG 节点 + 边 + 输入输出契约）
├── configs/                       # 配置规格
│   └── <spec_name>.yaml           # ConfigSpec YAML 投影
├── snapshots/                     # 实验快照元数据（不复制快照内容，仅元数据 + 引用）
│   └── <snapshot_id>.json         # ExperimentSnapshot 元数据（model_uri/metrics_json/git_sha）
└── lineage/                       # 血缘记录
    └── <record_id>.json           # LineageRecord（target/source_type/source_ref/inputs/outputs/operation）
```

### 2. `manifest.json` 结构

```json
{
  "format_version": "1.0.0",
  "exported_at": "2026-07-14T12:00:00Z",
  "exported_by": "user_id_or_plugin_id",
  "source_machine": {
    "hostname": "workshop-pc-01",
    "app_version": "4.0.0",
    "platform": "win32"
  },
  "project": {
    "project_id": "uuid",
    "name": "LTC-ChatterPredictor-Demo",
    "description": "LTC 颤振预测示例项目",
    "author": "张三",
    "remote_url": "",
    "current_branch": "main",
    "current_commit": "abc1234"
  },
  "resources": [
    {
      "resource_type": "dataset",
      "resource_uri": "dataset://<dataset_id>/1.0.0",
      "content_hash": "sha256:...",
      "path_in_package": "datasets/<dataset_id>/versions/1.0.0/data.parquet",
      "size_bytes": 1024000,
      "metadata": { "row_count": 1000, "schema": {...} }
    },
    {
      "resource_type": "model",
      "resource_uri": "model://LTC-ChatterPredictor/1.0.0",
      "content_hash": "sha256:...",
      "path_in_package": "models/<model_id>/files/model.pt",
      "size_bytes": 50000000,
      "metadata": { "model_type": "lnn", "framework": "torch-2.1.0" }
    }
  ],
  "content_policy": "include_content",
  "total_size_bytes": 51024000,
  "checksum": "sha256:..."
}
```

**关键字段说明**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `format_version` | semver | 包格式版本，导入时校验兼容性 |
| `exported_at` | ISO8601 | 导出时间戳 |
| `exported_by` | string | 导出者 user_id 或 plugin_id |
| `source_machine` | object | 源机器信息（hostname/app_version/platform），用于诊断兼容性问题 |
| `project` | object | 项目元数据（与 `ProjectSyncManifest` 对齐） |
| `resources` | array | 资源清单（每个资源含 URI / hash / 包内路径 / 大小 / 元数据） |
| `content_policy` | enum | `metadata_only` / `include_content` / `small_files_only`（≤10MB） |
| `total_size_bytes` | int | 包总大小（未压缩前），用于导入前预估 |
| `checksum` | sha256 | 整个 manifest.json 自身的校验和（不含此字段） |

### 3. 内容策略（`content_policy`）

| 策略 | 说明 | 适用场景 |
|------|------|----------|
| `metadata_only` | 仅导出元数据，不打包资源内容 | 项目结构分享、文档归档 |
| `include_content` | 打包所有资源内容（默认） | 跨机器迁移、完整备份 |
| `small_files_only` | 仅打包 ≤10MB 的资源文件，大文件仅元数据 | 网络受限场景、邮件附件 |

### 4. 导入冲突策略

导入时若目标机器已存在同 URI 资源，按 `conflict_strategy` 处理：

| 策略 | 说明 |
|------|------|
| `skip` | 跳过冲突资源（保留目标机器已有版本，默认） |
| `overwrite` | 覆盖目标机器已有版本（危险，需二次确认） |
| `rename` | 重命名导入资源（URI 追加 `_imported_<timestamp>` 后缀） |
| `fail` | 遇到冲突立即报错，不导入任何资源（事务性） |

### 5. 新增契约 `app/contracts/project_package.py`

定义以下 dataclass 与枚举：

- `PackageFormatVersion`（常量）：当前为 `"1.0.0"`
- `ContentPolicy`（枚举）：`metadata_only` / `include_content` / `small_files_only`
- `ConflictStrategy`（枚举）：`skip` / `overwrite` / `rename` / `fail`
- `PackageResourceEntry`（dataclass）：`resource_type` / `resource_uri` / `content_hash` /
  `path_in_package` / `size_bytes` / `metadata`
- `PackageManifest`（dataclass）：`format_version` / `exported_at` / `exported_by` /
  `source_machine` / `project` / `resources` / `content_policy` / `total_size_bytes` /
  `checksum`
- `ExportOptions`（dataclass）：`content_policy` / `include_datasets` / `include_models` /
  `include_workflows` / `include_configs` / `include_snapshots` / `include_lineage` /
  `max_file_size_bytes`（small_files_only 阈值，默认 10MB）
- `ImportOptions`（dataclass）：`conflict_strategy` / `target_owner_id` /
  `reinit_git`（导入后是否重新 git init）/ `dry_run`（仅校验不实际写入）
- `ExportResult`（dataclass）：`package_path` / `manifest` / `resource_count` /
  `total_size_bytes` / `skipped_resources`（因策略跳过的资源列表）
- `ImportResult`（dataclass）：`project_id` / `imported_resources` / `skipped_resources` /
  `renamed_resources` / `failed_resources` / `warnings`

### 6. 新增服务层 `app/services/project_package_service.py`

`ProjectPackageService` 单例，职责：

- **导出**：`export_project(project_id, output_path, options) -> ExportResult`
  - 调用 `ProjectSyncService` 获取项目清单与资源引用
  - 按 `content_policy` 决定是否打包资源内容
  - 流式写入 ZIP（`zipfile.ZipFile` + 64KB 缓冲），避免内存爆炸
  - 计算 `sha256` 校验和，写入 `manifest.json`
- **导入**：`import_project(package_path, options) -> ImportResult`
  - 解压 `manifest.json`，校验 `format_version` 兼容性
  - 校验 `checksum` 完整性
  - 按 `conflict_strategy` 处理冲突
  - 流式写入资源文件到目标目录
  - 若 `reinit_git=True`，调用 `ProjectSyncService.init_project()` 重新初始化 Git 仓库
- **校验**：`validate_package(package_path) -> ValidationResult`
  - 不实际导入，仅校验包完整性（manifest / checksum / 资源 hash）
- **预览**：`preview_import(package_path) -> PackageManifest`
  - 返回清单，前端用于展示"即将导入的内容"对话框

线程安全：`_locks: dict[str, threading.Lock]` 按 project_id 串行化导出操作，
按 package_path 串行化导入操作。

### 7. 新增路由 `app/api/v1/project_packages.py`

prefix `/api/v1/project-packages`，8 个端点：

| # | 方法 | 路径 | 权限 | 说明 |
|---|------|------|------|------|
| 1 | POST | `/export` | `project_package:write` | 导出项目（流式生成 .lomo 包，返回下载 URL） |
| 2 | POST | `/import` | `project_package:write` | 导入项目（上传 .lomo 包，流式解析） |
| 3 | POST | `/validate` | `project_package:read` | 校验包完整性（不实际导入） |
| 4 | POST | `/preview` | `project_package:read` | 预览包内容（返回 manifest） |
| 5 | GET | `/exports` | `project_package:read` | 列出已导出的包（分页） |
| 6 | GET | `/exports/{export_id}` | `project_package:read` | 查询导出记录详情 |
| 7 | DELETE | `/exports/{export_id}` | `project_package:write` | 删除导出包文件 |
| 8 | GET | `/imports` | `project_package:read` | 列出导入历史记录（分页） |

**导出/导入为长任务**：大项目导出可能耗时数分钟，采用"提交任务 + 轮询状态 +
下载"模式：
- `POST /export` 立即返回 `export_id` + `status=pending`，后台异步执行
- 前端轮询 `GET /exports/{export_id}` 直到 `status=completed`
- 完成后返回 `download_url`，前端通过该 URL 下载 `.lomo` 文件

### 13. 文件上传/下载实现

**上传（导入）**：使用 `multipart/form-data`，前端通过 `<input type="file">` 选择
`.lomo` 文件，axios POST 上传。后端使用 `python-multipart` 解析，流式写入临时目录，
解析 manifest 后启动后台导入任务。

**下载（导出）**：导出完成后，前端通过 `download_url`（如
`/api/v1/project-packages/exports/{export_id}/download`）下载 `.lomo` 文件。后端
使用 `StreamingResponse` 流式返回，避免内存占用。

## 理由

### 考虑的方案

1. **方案 A: 复用 Git bundle（`git bundle create`）**
   - 优点：原生 Git 支持，无需自定义格式
   - 缺点：Git bundle 仅打包 Git 对象，不含工作区文件，目标机器需 `git clone`
     bundle 才能恢复，且 bundle 不含资源内容（资源仍在 storage_uri 指向的外部
     路径）；无法表达"内容自包含"语义；无法支持 `metadata_only` / `small_files_only`
     策略；跨 Git 版本兼容性问题

2. **方案 B: 自定义 ZIP 归档 + JSON 清单 + 内容寻址**（**已选**）
   - 优点：完全自包含（含资源内容）；格式版本化便于演进；流式导出避免内存爆炸；
     校验和防止传输损坏；支持多种内容策略；与 ADR-011 Git 同步互补（导入后可
     继续 Git 同步）；与 ADR-012 资源卡片对齐（manifest.resources 复用 URI 体系）
   - 缺点：自定义格式需自行维护兼容性；大文件打包耗时（通过流式写入 + 后台任务
     缓解）

3. **方案 C: 使用 tar.gz 归档**
   - 优点：Linux 原生支持，无需额外依赖
   - 缺点：Windows 默认不支持 tar.gz（需 7-Zip 或内置 tar）；随机访问困难（必须
     全量解压才能读取 manifest）；ZIP 在 Windows / macOS / Linux 均有原生支持，
     且 `zipfile` 标准库流式写入性能足够

**选择方案 B** 的关键理由：
- 自包含是核心需求：跨机器迁移后项目立即可用，无需额外下载资源
- ZIP 跨平台兼容性最佳（Windows 资源管理器原生支持，用户可手动解压检查内容）
- 格式版本化为未来演进预留空间（如增加增量包、差分包）
- 与 ADR-011 / ADR-012 的 URI 体系对齐，复用现有 `ProjectSyncService` /
  `ResourceCardService` 的资源寻址逻辑

### 与 ADR-011 Git 同步的关系

| 维度 | ADR-011 Git 同步 | ADR-015 .lomo 包 |
|------|------------------|-------------------|
| 同步方式 | 引用同步（仅 hash） | 内容同步（含文件） |
| 依赖 | Git 远端 | 无（离线） |
| 适用场景 | 在线协作、版本管理 | 离线迁移、备份、模板发布 |
| 资源内容 | 不打包 | 打包（按 content_policy） |
| 冲突处理 | Git merge / rebase | 4 种策略（skip/overwrite/rename/fail） |
| 导入后状态 | 直接是 Git 仓库 | 可选 reinit_git 重新初始化 |

两者互补：用户可在有 Git 远端时用 ADR-011 在线协作，在无网络时用 ADR-015 离线
迁移；导入 .lomo 包后若配置了远端，可继续用 ADR-011 push/pull。

## 后果

### 积极影响

- 项目可在无网络环境下跨机器迁移，适配车间隔离网络
- 资源内容自包含，导入后立即可用，无需额外下载
- 模板市场可扩展支持"完整项目模板"（含示例数据集与预训练模型）
- 提供统一的备份格式，用户可一键归档整个项目
- 格式版本化为未来增量包、差分包预留空间

### 消极影响

- 新增 2 张表 + 1 个服务 + 1 个路由 + 前端契约/store，代码量增加
- 大项目导出耗时（通过后台任务 + 流式写入缓解，UI 需展示进度）
- .lomo 包可能很大（含模型文件时），需前端提示用户磁盘空间
- 自定义格式需维护兼容性（通过 `format_version` + 导入时版本校验缓解）

### 后续工作

- 增量包支持：基于 `format_version 1.1.0` 增加增量包格式（仅打包变化资源）
- 模板市场扩展：模板市场支持上传"完整项目模板"（.lomo 包）
- 加密包支持：敏感项目导出时支持密码加密（AES-256）
- 进度推送：导出/导入进度通过 WebSocket 推送（当前为轮询）
