# ADR-005: 核心架构契约设计（生态化演进地基）

**日期**: 2026-07-13
**状态**: 提议
**决策者**: 项目负责人（独立开发）

---

## 背景

灵境制造 v2.5.0 已具备完整的功能层（LTC 颤振预测、RAG、SHARP 智能体、插件系统、任务系统、飞轮指标、Tauri 桌面壳），但当前架构是"功能堆叠"而非"生态平台"：

**已有基础设施（可复用，不需要重写）**：
- 任务执行层 `app/tasks/task_system.py`：AsyncTaskManager 单例，状态机（PENDING/QUEUED/RUNNING/COMPLETED/FAILED/CANCELLED）+ DB 持久化 + Redis 进度 + 重试/取消/SSE/幂等/恢复
- 插件系统 `app/plugins/`：marketplace + 依赖解析 + 能力授权 + 工作进程隔离 + 健康检查
- MLflow 软依赖集成 `app/ai/lnn/tracking/mlflow_tracker.py`：记录超参/指标/模型 artifact
- 可复现性种子 `app/ai/lnn/training/reproducibility.py`：完整覆盖 random/np/torch/cudnn/DataLoader
- Prometheus metrics `app/utils/utils.py:MetricsCollector`：标准 exposition format
- 结构化日志 `app/core/logging_config.py`：JSONFormatter + 两层脱敏 + RingLogBuffer
- 前端任务面板 `src/views/TaskBoard.vue` + SSE `src/composables/useEventSource.ts`
- 统一 IPC 封装 `src/composables/useBackendStatus.ts` + HTTP 层 `src/utils/http.ts`

**关键 gap（阻碍生态化）**：
1. 任务系统只到"单任务执行"，无 DAG 编排/工作流模板/断点续跑
2. 数据层无 schema/版本/hash/数据集抽象（`data_lake.py` 仅 JSONL 追加）
3. MLflow 未记录 git SHA / 数据 hash，无实验快照/一键复现入口
4. 前端无插件化机制（动态组件/工作区扩展点）
5. 飞轮只有指标 API（`flywheel_metrics.py` 返回硬编码模拟值），无真实反馈闭环
6. 配置系统是 dataclass + env，无声明式 YAML + 继承/覆盖
7. 无面向用户的 Python SDK / CLI（只有 MCP CLI）
8. 无协作层（项目导入导出/Git 同步）
9. 无可解释性可视化（LTC 隐状态/注意力/反事实）
10. ADR 集合无任何可观测性/复现性/插件化主题

**核心问题**：如果直接开始重写所有模块，半年后所有模块都是 v0.1 半成品；如果只做局部优化，每加一个模块都要返工。需要先定**架构契约**，让后续每个模块都长在同一套接口上。

## 决策

定义五大核心契约（任务/数据/插件/配置/可观测），所有现有模块按契约重构，所有新模块按契约接入。契约一旦确定，后续阶段实现可在不破坏契约的前提下迭代。

详细契约接口定义见 [核心架构契约设计](../development/core-contracts-design.md)。

### 契约总览

| 契约 | 核心抽象 | 现有基础 | 改造方向 |
|------|---------|---------|---------|
| 任务契约 | `Task` / `Workflow` (DAG) | AsyncTaskManager | 增加 Workflow 编排层 + 任务模板 |
| 数据契约 | `Dataset` / `Version` / `Lineage` | data_lake.py | 重写为带 schema/版本/hash 的 Dataset 抽象 |
| 插件契约 | `Plugin` / `ExtensionPoint` | plugin_system.py | 后端已成熟，增加前端扩展点机制 |
| 配置契约 | `ConfigSpec` (YAML + 继承) | config.py | 增加声明式 YAML 实验配置层 |
| 可观测契约 | `Trace` / `Metric` / `Log` / `Snapshot` | metrics + logging + MLflow | 统一埋点格式 + 实验快照入口 |

### 关键设计原则

1. **契约优先，实现次之**：先定接口，后做实现。契约变更需走 ADR 评审
2. **核心 vs 插件边界明确**：核心只保留"任何模块都需要"的能力（任务/数据/配置/可观测/插件框架本身），业务模块（LTC/RAG/SHARP/仿真/CAM）全部插件化
3. **后端契约 Python 实现，前端契约 TypeScript 实现**：两端契约通过 OpenAPI 自动同步
4. **不破坏现有功能**：所有重构在新增模块中进行，旧模块通过 adapter 适配契约，验证通过后再切换
5. **分阶段交付**：每阶段 2-4 周，独立可发布，不积累大爆炸式重写

## 理由

### 考虑的方案

1. **方案 A: 全量重写所有模块**
   - 优点：架构最干净
   - 缺点：半年无产出，LTC 论文耽搁，半成品风险高
   - **否决**

2. **方案 B: 局部优化，不定契约**
   - 优点：短期见效快
   - 缺点：每加一个模块都要返工，架构债务持续累积，永远到不了生态
   - **否决**

3. **方案 C: 先定契约，分阶段按契约重构（本方案）**
   - 优点：架构不返工，每阶段可发布，LTC 论文不受影响，新模块即插即用
   - 缺点：前期 1-2 周不产出功能（只定契约），需要克制"立刻写功能"的冲动
   - **采纳**

### 选择理由

- 现有基础设施已相当成熟（任务/插件/MLflow/metrics/logging），破坏性重写是浪费
- gap 集中在"编排层"和"契约层"，不是"执行层"，改造成本可控
- 用户独立开发，时间精力有限，必须用契约降低后续每加一个模块的边际成本
- 学术成果（LTC 论文）依赖软件可信度，契约化让论文实验复现性有保障

## 后果

### 积极影响
- 后续每加一个模块（包括世界模型/RL）都长在同一套接口上，零返工
- 实验复现性从"软承诺"变为"硬契约"（git SHA + 数据 hash 强制记录）
- 前端插件化让第三方贡献工作流成为可能，生态起步
- ADR 治理覆盖可观测性/复现性/插件化盲区

### 消极影响
- 前 1-2 周只产出契约文档，不产出功能（开发节奏放缓）
- 现有模块需要写 adapter 适配契约，短期代码量增加
- 契约设计若有偏差，后续修改成本高（需走 ADR 评审流程）

### 技术影响
- 后端：新增 `app/contracts/` 目录承载所有契约抽象基类
- 前端：新增 `src/contracts/` 目录承载 TypeScript 契约类型
- 数据库：新增 `datasets` / `workflow_runs` / `experiment_snapshots` 表
- 依赖：可能引入 pydantic v2（数据契约）、networkx（DAG）、typer（CLI）

### 业务影响
- 软件从"工具集"演进为"平台"，可承载第三方插件
- 学术实验可复现，论文可信度提升
- 为世界模型 + RL 模块预留接入点

## 实施计划

### 阶段 0: 契约定型（1-2 周，不写功能代码）
- 落盘本 ADR + 详细契约设计文档
- 在 `app/contracts/` 和 `src/contracts/` 创建契约抽象基类
- 定义 OpenAPI schema 自动生成机制
- **产出**：契约代码骨架 + 单元测试（测契约本身）

### 阶段 1: 任务编排系统（2-3 周）
- 在 AsyncTaskManager 之上增加 Workflow 编排层（DAG + 任务模板 + 断点续跑）
- 前端 TaskBoard 扩展为 Workflow 面板
- **产出**：可定义"数据预处理→训练→评估→生成报告"DAG，一键跑通

### 阶段 2: 可复现性基础设施（2-3 周）
- 重写 data_lake 为 Dataset 抽象（schema/版本/hash）
- MLflow 集成强制记录 git SHA + 数据 hash
- 新增"实验快照"API + "一键复现"入口
- **产出**：每次训练自动生成可重放 snapshot

### 阶段 3: 插件系统骨架 + 配置系统（3-4 周）
- 后端插件系统重构（按契约）
- 前端插件化机制（工作区扩展点 + 动态组件）
- 声明式 YAML 配置系统（继承/覆盖/sweep）
- **产出**：第三方可贡献插件，前端工作区可扩展

### 阶段 4: 数据飞轮（2-3 周）
- 反馈采集层（用户标注/采纳/修正）
- 模型迭代管线（数据湖→训练→评估→模型市场→热更新）
- 飞轮指标接入真实数据源（替换硬编码模拟值）
- **产出**：飞轮真实闭环

### 阶段 5: CLI + SDK + HTTP API 契约（2 周）
- Python SDK（`from lomo import Workflow, Dataset`）
- 用户 CLI（`lomo train/predict/list`）
- HTTP API 版本化契约
- **产出**：软件可被脚本/notebook 调用

### 阶段 6: 工作流模板 + 协作层（2-3 周）
- 工作流模板市场
- 项目级 Git 同步
- 模型/数据集卡片
- **产出**：生态内容飞轮

### 阶段 7: 可解释性可视化（2 周）
- LTC 隐状态/注意力可视化
- 反事实解释
- 置信度披露
- **产出**：power user 粘性

### 阶段 8: 世界模型/RL 模块（远期，作为插件接入）
- 世界模型作为"过程状态预测器"插件
- RL agent 作为"决策策略"插件
- 嵌入工作流模板
- **产出**：完整"感知-预测-决策"闭环
