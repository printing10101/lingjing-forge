# ADR-019: 车间落地准备（cam_report.json → 真实车间试切的全链路差距分析与准备清单）

**日期**: 2026-07-14
**状态**: 已接受（P1-1 验证 51/51 通过、P1-2 联调 30/30 通过；P2-1 PyCAM 后端真实可用、P2-4 降级链路 7/7 通过；P2-2/P2-3/P3 待执行）
**决策者**: 项目负责人（独立开发）
**前置 ADR**: [ADR-018-CAM校验.md](ADR-018-CAM校验.md)（阶段 7 产物 cam_report.json 是车间落地的上游起点）
**关联**: ADR-005（核心架构契约）、ADR-013（颤振预测）、ADR-014（G 代码生成）、ADR-018（CAM 校验）

---

## 背景

阶段 0–7 全链路已实现并通过验收（ADR-018 验收 22/22、性能基准 26/26、阶段 7 独立验证 51/51、阶段 6→7 端到端联调 30/30）。系统当前能从「照片」一路走到「CAM 校验报告 JSON」：

```
照片 → 3D 重建 → 几何特征 → 参数化几何 → 切削参数 → 颤振预测 → G 代码 → CAM 校验 → cam_report.json
```

但 `cam_report.json` 是**软件链路的终点**，不是**车间落地的起点**。从「CAM 校验通过」到「真实机床切出合格零件」之间仍存在大量工程差距、合规门槛与风险待消解。本 ADR 不规划新的软件功能，而是规划**车间落地的准备清单、差距分析与风险缓解措施**。

### 项目记忆硬约束（车间落地必须遵守）

- 用户明确优先考虑真实工程生产环境而非学术价值（2026-07-13 决策）
- 工业生产硬门槛：良品率（0 缺陷容忍）、配合面公差 0.01mm、CNC 操作员执照 + 导师签字 + 保险
- mesh → 参数化 CAD 自动转换是工业界未解难题；生产系统依赖 human-in-the-loop（工程师确认特征）
- 生成的 G 代码必须通过现有 CAM 软件（NX / PowerMill / PyCAM）二次校验后才能上机；系统绝不直接接口 CNC 控制器
- 大一独立项目无法独立完成物理机床执行环节（需持证操作员 + 导师签字 + 保险）
- `cam_validation_required` 始终 True，`allow_delete_succeeded` 始终 False
- 阶段 7 产物终止于 cam_report.json，不触及物理机床（ADR-018 硬边界）

### 当前链路状态（截至 2026-07-14）

| 阶段 | 产物 | 状态 | 车间落地差距 |
|------|------|------|--------------|
| 1 | 点云 / mesh | 已完成 | 真实零件拍照环境（光照 / 反光 / 多角度覆盖）未验证 |
| 2 | 几何特征 JSON | 已完成 | 复杂特征（自由曲面 / 倒角 / 螺纹）识别率未在真实零件上验证 |
| 3 | STEP + OperationPlan 草案 | 已完成 | STEP 文件在 NX / SolidWorks 中的可编辑性未验证 |
| 4 | ChatterParams JSON | 已完成 | 切削参数库对真实材料批次（如 6061-T6 不同炉号）的覆盖不足 |
| 5 | ChatterReport JSON | 已完成 | HRC52 `pending_calibration` 标注未在真实切削试验中校准 |
| 6 | G 代码 + report.json | 已完成 | G 代码在真实 Fanuc / Siemens 控制器上的可执行性未验证 |
| 7 | cam_report.json | 已完成 | 内部预校验通过 ≠ CAM 软件二次校验通过 ≠ 机床可加工 |

### 核心差距

软件链路在「internal_only」CAM 后端下仅完成 **AABB 包围盒级快速预筛**（ADR-018 明确说明不可替代 CAM 软件二次校验）。要走到真实车间试切，必须补齐：

1. **CAM 软件二次校验落地**：NX Open / PowerMill / PyCAM 至少一套真实可用
2. **G 代码控制器兼容性验证**：在真实 Fanuc 0i / Siemens 840D 控制器上空运行
3. **切削参数库扩充**：覆盖真实车间常用材料批次与刀具库存
4. **颤振预测模型校准**：HRC52 待校准数据需真实切削试验补全
5. **合规链路打通**：持证操作员 + 导师签字 + 保险 + 车间安全规程
6. **试切件质量检测**：三坐标测量 + 表面粗糙度 + 良品率统计

## 决策

采用「**三阶段递进式车间落地准备**」方案，按风险从低到高、合规门槛从易到难分阶段推进。**不追求一步到位上机床**，而是先补齐软件链路到 CAM 软件二次校验的最后一公里，再推进到机床空运行，最后才考虑真实试切。

### 阶段划分

#### P1：软件链路落地准备（已完成 ）

**目标**：验证阶段 6→7 端到端联调在真实产物上稳定可用，为 CAM 软件二次校验提供可信输入。

- **P1-1**：阶段 7 独立验证脚本（`standalone_verify_cam_validation.py`，51/51 通过）
- **P1-2**：阶段 6→7 端到端联调脚本原型（`standalone_integration_stage6_to_stage7.py`，30/30 通过）
  - 使用真实阶段 6 产物 `gc_625e7706-...report.json` 作为输入
  - 调用 `CamValidationPipeline` 四步链：`create_task → run_pipeline → review_task → confirm_task`
  - 验证 `cam_report.json` 12 个顶层必填字段 + `cam_software_report` 嵌套对象 + `industrial_hard_gates_note` CNC 边界告知 + SUCCEEDED 禁删硬约束
  - 产出：`outputs/cam_validation/cam_*/cam_*.cam_report.json` + `cam_*.internal_report.json`

#### P2：CAM 软件二次校验落地（P2-1 / P2-4 已完成 ；P2-2 / P2-3 待执行）

**目标**：让 `cam_backend` 从 `internal_only` 升级到至少一套真实 CAM 软件可用，使 `cam_report.json` 携带真实 CAM 软件校验结论。

- **P2-1**：PyCAM 后端真实可用（开源、无授权门槛、Python 原生集成）
  - 安装 PyCAM：`pip install pycam`
  - 验证 `CamAdapter` 的 `pycam` 后端调用链：subprocess 启动 → G 代码加载 → 刀轨仿真 → 碰撞报告回传
  - 在 P1-2 联调脚本基础上新增 `pycam` 后端模式测试用例
  - 产出：`cam_report.json` 的 `cam_software_report.backend_used` 从 `internal_only` 升级为 `pycam`
- **P2-2**：PowerMill 后端真实可用（需授权，导师实验室资源）
  - 验证 `scripts/cam_adapters/powermill/autorun_gcode_check.mac` 宏文件在 PowerMill 中可执行
  - 验证 subprocess 调用链：PowerMill CLI 启动 → 宏执行 → 碰撞报告 JSON 回传
  - 产出：`cam_report.json` 的 `cam_software_report.backend_used` 可为 `powermill`
- **P2-3**：NX Open 后端真实可用（需授权 + NX Open Python 环境）
  - 验证 `scripts/cam_adapters/nx_open/autorun_gcode_check.py` 在 NX Open Python 环境中可执行
  - 验证 subprocess 调用链：NX 启动 → Python 脚本执行 → 碰撞报告 JSON 回传
  - 产出：`cam_report.json` 的 `cam_software_report.backend_used` 可为 `nx_open`
- **P2-4**：CAM 后端降级链路验证
  - 模拟 NX / PowerMill / PyCAM 均不可用场景，验证自动降级到 `manual` 模式
  - 验证 `manual_checklist_path` 生成的校验清单文档完整性
  - 产出：`cam_software_report.degraded=True` + `degradation_reason` 非空 + `manual_checklist_path` 文件存在

#### P3：车间试切准备（待执行，需导师 + 操作员介入）

**目标**：在合规框架下完成首次真实车间试切，验证全链路在真实加工环境中的可行性。

- **P3-1**：G 代码控制器兼容性验证（机床空运行，不上工件）
  - 将阶段 6 生成的 `.nc` 文件加载到真实 Fanuc 0i / Siemens 840D 控制器
  - 空运行验证：无报警、无超程、刀位正确、换刀顺畅
  - **合规要求**：持证操作员操作 + 导师在场 + 车间安全规程遵守
  - 产出：`gcode_controller_compatibility_report.json`（含控制器型号、空运行结果、报警记录）
- **P3-2**：切削参数库扩充
  - 收集真实车间常用材料批次（6061-T6 / 45#钢 / HRC52 / TC4）的切削参数
  - 扩充 `app/cutting_parameters/material_database.json`（或对应数据源）
  - 验证 `CuttingParametersRecommender` 对新批次材料的推荐合理性
  - 产出：扩充后的材料数据库 + 推荐结果对比报告
- **P3-3**：颤振预测模型校准试验
  - 设计 HRC52 待校准材料的切削试验方案（与导师协商）
  - 采集真实振动 / 声发射 / 力信号
  - 用真实数据校准 LTC 预测模型，消除 `pending_calibration` 标注
  - **合规要求**：试验方案需导师签字 + 车间保险 + 操作员持证
  - 产出：校准后的 LTC 模型 + 校准试验报告 + `pending_calibration` 标注移除
- **P3-4**：首次试切件质量检测
  - 基于 P3-1 ~ P3-3 的成果，加工首个试切件
  - 三坐标测量：关键尺寸公差（配合面 0.01mm）
  - 表面粗糙度测量：Ra 值
  - 良品率统计：0 缺陷容忍门槛
  - 产出：`first_part_quality_report.json`（含尺寸测量、粗糙度、良品率、缺陷记录）
- **P3-5**：合规链路归档
  - 持证操作员签字记录
  - 导师签字记录
  - 车间保险凭证
  - 试切件质量报告
  - 全链路产物归档（照片 → cam_report.json → 试切件检测报告）
  - 产出：`workshop_landing_archive.json`（合规归档索引）

### 工业硬门槛（P3 阶段必须满足）

| 门槛 | 指标 | 验证方式 |
|------|------|----------|
| 良品率 | 0 缺陷容忍 | 三坐标测量 + 表面粗糙度检测 |
| 配合面公差 | 0.01mm | 三坐标测量 |
| CNC 操作员 | 持证 | 操作员证件复印件归档 |
| 导师签字 | 必须 | 签字记录归档 |
| 车间保险 | 必须 | 保险凭证归档 |
| G 代码二次校验 | CAM 软件通过 | `cam_report.json` 的 `cam_software_report.status=passed` |
| 控制器兼容性 | 空运行无报警 | `gcode_controller_compatibility_report.json` |

### 系统定位重申（不可逾越）

本系统定位为「**工程师助手**」，非「全自动生产线」。车间落地过程中，系统始终处于 human-in-the-loop 模式：

```
系统生成 G 代码 → 工程师审核 → CAM 软件二次校验 → 工程师确认 →
持证操作员加载到机床 → 空运行验证 → 试切 → 质量检测 → 归档
```

系统绝不：
- 直接接口 CNC 控制器
- 跳过 CAM 软件二次校验
- 跳过工程师审核
- 跳过持证操作员 + 导师签字
- 自主决定上机加工

## 理由

### 为什么不一步到位上机床

1. **合规门槛高**：CNC 操作员执照 + 导师签字 + 保险，任一缺失即无法上机
2. **风险不可控**：G 代码在真实控制器上的行为未验证，可能损坏机床或工件
3. **数据不充分**：HRC52 `pending_calibration` 标注说明预测模型未校准，直接上机风险高
4. **CAM 软件未落地**：`internal_only` 后端仅 AABB 预筛，不可替代真实 CAM 校验
5. **大一独立项目约束**：无法独立完成物理机床执行环节

### 为什么选择 PyCAM 作为 P2-1 首选

1. **开源免费**：无授权门槛，独立项目可负担
2. **Python 原生**：与现有 FastAPI 后端无缝集成，subprocess 调用链简单
3. **G 代码原生支持**：直接读取 `.nc` 文件，无需格式转换
4. **碰撞检测能力**：支持 3 轴刀轨仿真 + 碰撞报告，满足阶段 7 二次校验需求
5. **降级路径清晰**：PyCAM 不可用时仍可降级到 `manual` 模式

### 为什么 PowerMill / NX Open 排在 P2-2 / P2-3

1. **授权依赖**：需导师实验室资源，不能独立完成
2. **环境复杂**：NX Open 需要独立 Python 环境，PowerMill 需要宏文件调试
3. **优先级低**：PyCAM 满足基本二次校验需求后，PowerMill / NX Open 是锦上添花

### 考虑的方案

1. **方案 A**：三阶段递进式（P1 软件链路 → P2 CAM 软件 → P3 车间试切）
   - 优点：风险递进、合规门槛递进、每阶段可独立验收、失败可回退
   - 缺点：周期长，P3 阶段依赖外部资源（导师 / 操作员 / 保险）

2. **方案 B**：直接跳到车间试切（跳过 P2 CAM 软件落地）
   - 优点：周期短
   - 缺点：违反 ADR-018 硬边界（`internal_only` 不可替代 CAM 软件二次校验）、风险不可控、合规不通过

3. **方案 C**：仅完成 P2 CAM 软件落地，不做车间试切
   - 优点：合规风险最低
   - 缺点：无法验证全链路在真实加工环境中的可行性、用户明确要求车间落地、学术价值不足（论文需真实试验数据）

**选择方案 A**：唯一兼顾合规、风险、用户需求的方案。

## 后果

### 积极影响

- 系统从「软件原型」升级为「车间可用工具」
- `cam_report.json` 携带真实 CAM 软件校验结论，可信度大幅提升
- 试切件质量数据可作为论文实验数据（Journal of Intelligent Manufacturing）
- HRC52 `pending_calibration` 标注可通过 P3-3 校准试验消除
- 全链路产物归档满足审计 / 合规 / 论文引用需求

### 消极影响

- P3 阶段依赖外部资源（导师 / 操作员 / 保险），进度不可控
- 试切件质量检测可能暴露链路缺陷，需要返工
- 真实车间环境噪声 / 振动可能影响颤振预测模型精度，需要重新校准
- P3-3 校准试验需要真实切削数据采集，周期长

### 技术影响

- `CamAdapter` 需支持真实 CAM 软件调用（PyCAM / PowerMill / NX Open）
- `cam_store.py` 的 `CamSoftwareReport` 字段需在真实 CAM 软件调用下验证完整性
- 切削参数库需扩充，可能需要重构 `CuttingParametersRecommender` 数据源
- LTC 预测模型需用真实数据重新训练 / 校准
- 新增产物类型：`gcode_controller_compatibility_report.json` / `first_part_quality_report.json` / `workshop_landing_archive.json`

### 业务影响

- 系统定位从「工程师助手原型」升级为「车间可用工程师助手」
- 用户学术目标（清华机械考研、Journal of Intelligent Manufacturing 投稿）获得真实试验数据支撑
- 满足用户明确优先的「真实工程生产环境」需求（2026-07-13 决策）
- 大一独立项目在合规框架下完成首次车间试切，具备示范意义
