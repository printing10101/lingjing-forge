#1 硬编码个人用户名路径（Rust sidecar）
engineering/src-tauri/src/sidecar.rs:667
resolve_python_path() 中硬编码了 C:\Users\\anaconda3\python.exe 等多个含用户名的路径。 当应用分发给其他用户时，Python 解释器查找将失败，导致整个桌面应用无法启动。 虽然也定义了 LINGJING_PYTHON_PATH 环境变量优先级更高，但默认回落路径中不该包含硬编码的个人目录。 
let candidates = [
    r"C:\Users\\anaconda3\python.exe",        // ← P0: 硬编码用户名
    r"C:\ProgramData\anaconda3\python.exe",
    r"C:\Python313\python.exe",
    r"C:\Users\\AppData\Local\Programs\Python\Python313\python.exe",  // ← 同上
];
修复方案：移除所有含 C:\Users\ 的路径，保留通用路径（ProgramData、C:\Python3xx、%LOCALAPPDATA%）。使用 std::env::var("LOCALAPPDATA") 动态获取用户 AppData 目录。

#4 state/manager.py 静默吞异常——数据库故障无感知
engineering/python/app/state/manager.py
状态管理器中有 3 处 except Exception: pass，当数据库写入失败（磁盘满、锁冲突等）时静默丢弃数据，且没有任何日志或告警。这是典型的数据完整性隐患。 
# P0: 数据库写入失败静默丢弃
except Exception:
    pass  # ← 数据可能永久丢失，无日志
修复方案：至少记录 ERROR 级别日志 + 递增 consecutive_failures 计数器。超过阈值时触发健康检查告警。考虑引入死信队列（dead-letter queue）暂存失败数据。
#5 exec() 动态代码执行（2处独立入口）
cadquery_gen.py:591 + skill_compiler.py:95,125 + sandbox_executor.py:66
代码中存在 4 处 exec() 调用用于执行用户提交的 CadQuery 脚本和 Skill 代码。虽然已实施 AST 审计、受限 globals、超时控制等多层防护，但 exec() 本质上是不可完全安全的操作。两个入口（CadQuery 和 Skill Loader）各自实现了独立的安全沙箱，且 skill_compiler.py 还有降级路径 _compile_code_in_process（无 RestrictedPython 时的 fallback）。 
# cadquery_gen.py:591 — CadQuery 脚本执行
exec(script, safe_globals)

# skill_compiler.py:95 — RestrictedPython 安全编译
exec(byte_code, restricted_globals)

# skill_compiler.py:125 — 降级路径（安全防护较弱）
exec(compiled, namespace)
修复方案：（1）统一两个 exec() 入口的安全审计逻辑为同一个模块；（2）skill_compiler 降级路径添加定期安全审计 + 降级时记录 WARNING 并建议安装 RestrictedPython；（3）考虑 WASM 沙箱替代 exec()（长期方案）；（4）确保 RestrictedPython 列为生产强制依赖，不允许降级。

P1 高风险应修复问题

#6 CSP 策略使用 'unsafe-inline'（违反 Tauri 安全规范）
engineering/index.html:31, splashscreen.html:25
script-src 和 style-src 均包含 'unsafe-inline'。项目记忆已明确要求移除 unsafe-inline，但至今未实现 nonce 机制替代。这是 XSS 防护的关键缺口。
修复方案：Vue3+Vite 可将内联脚本提取为外部 .js 文件；Element Plus 主题覆盖可改用 CSS Module 或提取为 .css 文件。实现 nonce 机制（Vite 插件自动注入）。
#7 145+ 全局单例 get_xxx() 模式——测试困难
engineering/python/app/ (全项目)
项目中存在 145+ 个 get_xxx() 风格的全局单例工厂函数（get_db, get_redis, get_tdengine, get_budget_enforcer, get_cost_tracker, get_plugin_manager...）。这些函数虽被标记为 "FastAPI Depends 兼容"，但实际是隐藏的运行时耦合——测试时需要 monkey-patch 全局状态才能隔离。
修复方案：逐个模块迁移到真正的 FastAPI Depends() 依赖注入模式。创建一个统一的 app/dependencies.py 集中注册所有依赖，确保每个依赖在测试中可以通过 app.dependency_overrides 替换。
#8 API 层越过服务层直接访问数据库（21处）
api/v1/ (21个文件)
19处 API 路由直接导入 app.models/，4处直接导入 app.database/，绕过服务层。涉及 auth, users, cost_budget, health, lnn, governance, goal_alignment 等核心模块。
修复方案：为每个域引入 Repository 模式（参考已有的 database/repository/machining_record_repo.py），API 层通过 Depends 注入 Service → Repository 链，禁止直接访问 models/database。

#11 TDengine SQL f-string 拼接（4处）

修复方案：将 UPDATE 动态列名也纳入参数化查询；为所有 SQL 拼接增加编译期检查（lint rule: 禁止 f-string 出现在 SQL 执行上下文）；增加 app/budget/sql_safety.py 统一 SQL 安全入口。
