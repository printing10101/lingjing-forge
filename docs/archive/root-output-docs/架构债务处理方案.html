二、目标架构（收敛方向）

后端 Clean Architecture

api/           路由 + 参数校验 + 编排
  └─ Depends(get_xxx)   ← 依赖注入（唯一入口）
application/   用例（服务编排，无 FastAPI）
domain/        领域模型 + 契约（定义于被消费包）
infrastructure/ DB / Redis / TDengine / Rust 桥

关键约束：API 不得 import app.database/app.models；get_* 只允许从 app.dependencies 导入。

前端 Feature-Sliced Design

views/       页面（只 import @/features，禁止 http）
features/    API 服务层（每模块覆盖该域全部端点）
shared/      通用（http 客户端 / 组件 / 工具）

关键约束：视图文件禁止 import http；features/*/api.ts 必须覆盖对应视图的全部调用端点。

三、分阶段处理方案

阶段 1 · 后端依赖治理（约 2 周）— 消 D1/D3/D4

目标：依赖注入成为唯一入口，API 层与数据层隔离，路由可统一审计。
① D1 单例消费方迁移
1. 以 docs/singleton_to_di_migration.md 为清单，按模块批量改 from app.xxx import get_xxx → from app.dependencies import get_xxx（行为一致，纯改导入）。
2. FastAPI 端点改为 Depends(get_xxx) 参数注入；CLI/worker 保留函数调用（依赖工厂本身已单例）。
3. 原模块 get_xxx 加 @deprecated 标记，跑全量 pytest 回归。
涉及：~60 文件风险：中（导入路径）验证：pytest 全量
② D3 API 直连 DB → Repository
1. 为 9 个直连点（agent_state/auth/cost_budget/goal_alignment/governance/users 等）各建 app/infrastructure/repositories/<域>_repo.py，封装 ORM 访问。
2. API 改为 Depends(get_<域>_repo) 调用 Repository 方法。
3. 单测覆盖 Repository（替代 API 内联 SQL 断言）。
涉及：9 文件 + 新 repo 层风险：中验证：pytest + 接口测试
③ D4 路由归位
1. main.py 的 6 条 @app.get 迁入 api/v1/ 对应 router。
2. 非 API 包 router（11 处）全部经 app/router_registry.py 统一挂载，删除散落 include_router。
3. 导出 OpenAPI 契约对比前后端点集（diff 保证零回归）。
涉及：~15 文件风险：低-中验证：OpenAPI diff
④ D8 测试安全网（与 ①②并行）
1. 先为核心主链补 5 条端到端测试：认证→3D 导入→工艺→NC→仿真→DNC。
2. 再为已迁移的 Repository/依赖工厂补单测（每迁移一个补一层）。
涉及：tests/ 新增风险：低验证：pytest + 覆盖率对比

阶段 2 · 前端激活（约 3 周）— 消 D2/D5/D7

目标：features/ 成为唯一 API 入口，巨型组件拆分，统一日志。
① D2 features/ 补齐 + 19 视图迁移
1. 逐视图审计 http 调用（已定位 19 处 import + 各 5-8 个调用点）。
2. 按域补全 features/*/api.ts 端点（含类型定义），直到覆盖视图全部调用。
3. 视图逐个替换为 import {...} from '@/features'，删 import http。
4. 每迁移 3-5 个视图跑一次 vue-tsc --noEmit + 相关测试。
涉及：19 视图 + 15 features 模块风险：中（端点覆盖是难点）验证：vue-tsc + Vitest
② D5/D7 God 模块拆分
1. 后端按已示范模式拆分：simulation/api.py → simulation/ 子包（routes/services/stages）；gcode_generator.py 按输出控制器分组。
2. 前端拆分 Simulation.vue(1884)/TaskBoard.vue/Workspace.vue → 子组件 + composable（复用 08-01 已完成的拆分模式）。
3. 引入统一日志：utils/logger.ts 封装，逐步替换 122 处 console.*。
涉及：8 后端文件 + 3 前端组件风险：中验证：py_compile + vue-tsc + 冒烟

阶段 3 · 工程化收口（持续，约 2 周集中 + 常态化）— 消 D6/D9

① D6 类型抑制清理
1. 引入 mypy（--ignore-missing-imports）+ pyright 建立基线，将现有 119 type:ignore 写入允许清单。
2. 每 PR 限制新增抑制数（CI 门槛），存量按"先易后难"分批消除：先清纯导入类、再清可收敛为具体类型的。
涉及：~80 文件风险：低（有基线兜底）验证：mypy/pyright CI
② D9 契约落地约定
1. 以 chatter_prediction/_types.py 为范式，确立约定：契约定义于被消费的领域包，禁止新建顶层共享目录。
2. 在 CONTRIBUTING.md 写入架构规则 + tests/architecture/ 已有 import 方向测试强化为 CI 强制。
涉及：CONTRIBUTING + architecture 测试风险：低验证：architecture pytest

四、依赖关系与建议顺序

  • 阶段 1 先行：D8 测试安全网是后续一切重构的前提——先补主链 E2E，再动单例/路由，回归才有保障。
  • D1→D3→D4 有依赖：先把 get_* 消费方统一到 dependencies，Repository 才能通过 Depends 注入。
  • D2 独立可并行：前端迁移不依赖后端阶段 1（接口契约不变，只改前端导入），可由第二人并行。
  • D6 持续化：类型基线建立后可随每个 PR 增量清理，不必集中冲刺。
量化目标：阶段 1 完成后——get_* 消费方 100% 走 dependencies；API 直连 DB 归零；OpenAPI 端点 diff 为零；主链 E2E ≥5 条。阶段 2 完成后——视图 import http 归零；无 >1000 行生产文件。届时复评预估：架构清晰度 52→70+、可维护性 52→68+、测试有效性 60→72+，综合可升至 ~70（B-）。
