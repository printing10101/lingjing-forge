## 3. 起步

### 3.1 第一次贡献

寻找 [`good first issue`](https://github.com/<org>/<repo>/issues?q=is%3Aopen+label%3A%22good+first+issue%22) 标签的 issue。

### 3.2 大功能开发

请先开 **Discussion / RFC** 说明：

- 背景与动机
- 设计方案
- 替代方案对比
- 影响范围（API 兼容性、性能、数据迁移）
- 测试计划

经核心维护者同意后再开始编码。

## 4. 分支管理

### 4.1 分支模型（Git Flow 变体）

```
main (受保护)
  │
  ├── release/v1.12.x       # 长期维护
  │     └── bugfix/xxx      # 紧急修复
  │
  ├── develop (集成分支)
  │     ├── feature/xxx     # 新功能
  │     ├── refactor/xxx    # 重构
  │     └── chore/xxx       # 杂项
  │
  └── hotfix/xxx            # 紧急生产修复（基于 main）
```

### 4.2 分支命名

格式：`<type>/<scope>-<short-desc>`

| 前缀 | 用途 | 示例 |
|------|------|------|
| `feature/` | 新功能 | `feature/lnn-hybrid-model` |
| `bugfix/` | Bug 修复 | `bugfix/dxf-parser-overflow` |
| `refactor/` | 重构 | `refactor/postprocess-base-class` |
| `hotfix/` | 紧急修复 | `hotfix/auth-token-revoke` |
| `docs/` | 文档 | `docs/api-error-codes` |
| `chore/` | 杂项 | `chore/bump-deps-2026q2` |
| `test/` | 测试 | `test/load-test-sse` |

> **scope** 推荐：模块名（`lnn` / `dxf` / `auth` / `frontend` / `docs` 等）。

### 4.3 受保护分支

| 分支 | 规则 |
|------|------|
| `main` | 禁止直接 push；需 PR + 2 名维护者批准 + CI 全绿 |
| `develop` | 需 PR + 1 名维护者批准 + CI 全绿 |
| `release/*` | 仅维护者可 push（cherry-pick 修复） |

## 5. 提交规范

### 5.1 Conventional Commits

```
<type>(<scope>): <subject>

<body>

<footer>
```

#### type

| type | 说明 | 影响 CHANGELOG |
|------|------|----------------|
| `feat` | 新功能 | |
| `fix` | Bug 修复 | |
| `docs` | 文档变更 | |
| `style` | 格式调整（不影响逻辑） | |
| `refactor` | 重构（既非 feat 也非 fix） | |
| `perf` | 性能优化 | |
| `test` | 测试相关 | |
| `build` | 构建系统/依赖变更 | |
| `ci` | CI 配置变更 | |
| `chore` | 杂项 | |
| `revert` | 回滚 | |

#### 示例

```
feat(lnn): 支持 Hybrid 模型推理并暴露置信度

- 新增 HybridModel 类（CNN+LNN 融合）
- API 响应增加 `confidence` 字段
- 添加单元测试与基准测试
- 更新 OpenAPI 规范

Closes #1234
Refs: #1230
```

### 5.2 提交信息检查清单

- [ ] subject 不超过 72 字符
- [ ] subject 不以句号结尾
- [ ] subject 使用祈使语气（"add" 而非 "added"）
- [ ] body 解释 **为什么** 而非 **做了什么**
- [ ] 引用相关 issue（`#1234`）或 PR（`#5678`）
- [ ] 破坏性变更在 footer 用 `BREAKING CHANGE:` 说明

### 5.3 破坏性变更

任何破坏性变更必须在 **body** 顶部用 `BREAKING CHANGE:` 说明：

```
feat(api): 移除已废弃的 /v1/lnn/predict 端点

BREAKING CHANGE: `/api/v1/lnn/predict` 已删除，请迁移至 `/api/v1/lnn/infer`。
旧端点自 v1.10.0 起标记 deprecated，移除后请更新客户端。

迁移指南：docs/api/migration/v1.10-to-v1.12.md
```

## 6. Pull Request 流程

### 6.1 提交流程

```bash
# 1. 同步最新 develop
git fetch origin
git checkout develop
git pull --rebase

# 2. 创建分支
git checkout -b feature/lnn-confidence-field

# 3. 编码（频繁提交）
git add -p
git commit -m "feat(lnn): add confidence field to infer response"

# 4. 推送
git push -u origin feature/lnn-confidence-field

# 5. 在 GitHub 上创建 PR（目标分支：develop）
gh pr create --base develop \
  --title "feat(lnn): 推理响应增加 confidence 字段" \
  --body-file .github/PULL_REQUEST_TEMPLATE.md
```

### 6.2 PR 标题与描述

#### 标题

遵循提交规范：`type(scope): 简明描述`。

#### 描述模板

参考 `.github/PULL_REQUEST_TEMPLATE.md`：

```markdown
## 变更说明
<!-- 简述本次 PR 的目的与实现方式 -->

## 关联 Issue
<!-- 关闭或引用相关 issue，例如 Closes #123 -->

## 变更类型
- [ ] Bug 修复（非破坏性）
- [ ] 新功能（非破坏性）
- [ ] 破坏性变更（需在描述中详细说明）
- [ ] 文档
- [ ] 重构
- [ ] 性能优化
- [ ] 测试
- [ ] CI/构建

## 测试
- [ ] 单元测试已通过
- [ ] 集成测试已通过
- [ ] E2E 测试已通过（如适用）
- [ ] 手动测试已完成

## 截图/录屏
<!-- UI 变更必填 -->

## 检查清单
- [ ] 代码遵循项目风格（ruff、black、ESLint、Prettier）
- [ ] 自我审查完成
- [ ] 关键路径加注释
- [ ] 相关文档已更新
- [ ] 无新警告
- [ ] 依赖变更已说明
```

### 6.3 PR 规模

| 规模 | 行数 | 建议 |
|------|------|------|
| 小 | < 200 | 最佳 |
| 中 | 200-500 | 可接受 |
| 大 | 500-1000 | 需拆分或加详细说明 |
| 巨型 | > 1000 | **必须** 拆分 |

### 6.4 Draft PR

还在迭代中时使用 Draft：

```bash
gh pr create --draft
```

完成后点击 `Ready for review`。

## 7. 代码审查

### 7.1 作者准备

提 PR 前自审：

- [ ] diff 阅读 2 遍
- [ ] 跑通本地测试
- [ ] 文档、注释、类型注解完整
- [ ] 提交信息规范
- [ ] CI 全部绿色

### 7.2 审查者职责

**响应时间 SLA**：

| 优先级 | 首次响应 | 完成审查 |
|--------|----------|----------|
| P0 | 4 小时 | 24 小时 |
| P1 | 1 工作日 | 3 工作日 |
| P2 | 3 工作日 | 1 周 |
| P3 | 1 周 | 2 周 |

### 7.3 审查维度

#### 7.3.1 正确性

- [ ] 逻辑是否符合需求
- [ ] 边界条件处理
- [ ] 错误处理是否合理
- [ ] 并发/竞态条件

#### 7.3.2 设计

- [ ] 是否符合现有架构
- [ ] 是否过度设计
- [ ] 是否可以复用现有组件
- [ ] API 设计是否合理

#### 7.3.3 可读性

- [ ] 命名是否清晰
- [ ] 函数/方法是否过短或过长（建议 ≤ 50 行）
- [ ] 复杂逻辑是否有注释
- [ ] 魔法数字是否提取为常量

#### 7.3.4 测试

- [ ] 关键路径有测试
- [ ] 测试用例是否充分（含异常路径）
- [ ] 是否有不必要的 mock
- [ ] 测试是否独立、可重复

#### 7.3.5 安全

- [ ] 输入是否校验
- [ ] 是否有 SQL 注入、XSS、SSRF 等风险
- [ ] 敏感信息是否加密
- [ ] 权限是否正确

#### 7.3.6 性能

- [ ] 是否有 N+1 查询
- [ ] 是否有不必要的循环
- [ ] 大对象是否需要分页/流式
- [ ] 缓存是否合理

#### 7.3.7 文档

- [ ] 公开 API 是否有 docstring
- [ ] 行为变更是否更新 CHANGELOG
- [ ] 用户可见变更是否更新用户手册

### 7.4 审查评论

#### 三种评论前缀

- `nit:` — 小问题，可不改
- `suggestion:` — 建议，可讨论
- `blocking:` — 必须修改才能合并

#### 示例

```
nit: 这个变量名建议用 `retry_count` 更清晰。

suggestion: 这里可以用 `functools.cache` 替代手写 dict。

blocking: 此处缺少输入校验，可能导致 SSRF。请使用 `app.utils.url.safe_request`。
```

### 7.5 解决评论

- 每条评论必须被显式 **解决**（通过 commit fix 或回复解释）
- 不同意时礼貌讨论，达成共识后处理
- 共同作者对最终代码质量负责

## 8. 代码风格

### 8.1 Python

- **格式化**：black（行宽 100）
- **导入**：ruff（isort 兼容）
- **Lint**：ruff
- **类型**：mypy 严格模式
- **命名**：
  - 函数/变量：`snake_case`
  - 类：`PascalCase`
  - 常量：`UPPER_SNAKE`
  - 私有：`_leading_underscore`
- **类型注解**：所有公开 API 必填

#### 配置

`pyproject.toml`：

```toml
[tool.black]
line-length = 100

[tool.ruff]
line-length = 100
target-version = "py311"

[tool.ruff.lint]
select = ["E", "F", "W", "I", "N", "UP", "B", "A", "C4", "PT", "RET", "SIM"]

[tool.mypy]
strict = true
python_version = "3.11"
```

### 8.2 TypeScript / Vue

- **格式化**：Prettier
- **Lint**：ESLint
- **类型**：TypeScript strict 模式
- **命名**：
  - 变量/函数：`camelCase`
  - 类/接口：`PascalCase`
  - 常量：`UPPER_SNAKE`
  - 组件：`PascalCase.vue`
- **Composition API**：统一使用 `<script setup lang="ts">`

### 8.3 SQL

- 关键字大写：`SELECT * FROM users WHERE id = $1`
- 表名/列名：`snake_case`
- 显式 JOIN，不用隐式
- 必须用参数化查询（防止 SQL 注入）

### 8.4 注释与文档

#### Python Docstring（Google 风格）

```python
def infer(model_id: str, input: dict, timeout: float = 30.0) -> InferenceResult:
    """执行 LNN 模型推理。

    根据 model_id 选择对应模型（CFC/LTC/Hybrid），
    加载后执行前向计算并返回结构化结果。

    Args:
        model_id: 模型标识符，如 "cfc_v3" / "ltc_v2" / "hybrid_v1"。
        input: 输入特征字典，必须包含 "features" 键。
        timeout: 单次推理超时时间（秒）。

    Returns:
        InferenceResult: 包含 prediction、confidence、provenance。

        ModelNotFoundError: model_id 不存在。
        InferenceTimeoutError: 推理超过 timeout。

    Example:
        >>> result = infer("cfc_v3", {"features": [0.1, 0.2]})
        >>> print(result.prediction)
    """
```

| 检查 | 工具 | 失败标准 |
|------|------|----------|
| Lint | ruff, ESLint | 任何错误 |

常见问题：

| 报错 | 修复 |
|------|------|
| `black would reformat` | 本地 `black .` |
| `ruff: F401 imported but unused` | 删除 import 或加 `# noqa: F401` |
| `mypy: missing type hints` | 补全注解 |
| `Coverage < 80%` | 补测试 |
| `E2E timeout` | 检查端口与 webServer |

## 10. 发布流程

### 10.1 版本号（SemVer）

`MAJOR.MINOR.PATCH`

- **MAJOR**：破坏性变更
- **MINOR**：新功能（向后兼容）
- **PATCH**：Bug 修复（向后兼容）

### 10.2 流程

1. **冻结**：从 `develop` 创建 `release/v1.13.0`
2. **测试**：全量 E2E + 性能基准
3. **修 bug**：仅 cherry-pick bugfix 到 release 分支
4. **文档**：更新 CHANGELOG、用户手册、API 文档
5. **合并**：release → main + develop（带 `release-please` bot）
6. **打 tag**：`v1.13.0`
7. **发布**：
   - Docker 镜像：推 `ghcr.io/lingjing/lingjing-backend:v1.13.0`
   - 桌面包：CI 自动构建并签名
   - GitHub Release：附 CHANGELOG

### 10.3 CHANGELOG

由 `release-please` 自动生成，手动补充需在 `.release-please-manifest.json` 中维护。
