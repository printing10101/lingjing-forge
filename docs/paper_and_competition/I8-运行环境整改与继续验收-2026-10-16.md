## 1. 已完成的整改

### 1.1 CAD 计算正常但退出崩溃

此前 I7 的 356 项回归断言通过，但进程返回 3221225477（0xC0000005），不能算验收通过。
本轮分别运行 OCP、VTK、CasADi、NLopt 及其组合：单模块/OCP 与相应组合可正常退出，
CasADi 3.8.0 与 NLopt 同载即可复现，CadQuery 导入及体积计算也出现退出期错误。
不能把问题笼统归为 OCP 不可用。

上游 [CasADi #4403](https://github.com/casadi/casadi/issues/4403) 确认 Windows 的共享 SWIG 类型表冲突，
[3.8.1 版本](https://github.com/casadi/casadi/releases/tag/3.8.1)包含修复。
本地隔离安装 3.8.1 后，CasADi、NLopt、CadQuery 同载且计算 1×2×3 盒体体积为 6，正常退出。
最终系统 Python 3.14 通过用户 site-packages 加载 3.8.1，独立新进程重复三次均退出 0。
生产 requirements 也固定为 3.8.1，避免桌面重建再次带入旧版本。

系统目录中的旧原生文件被已有进程占用，直接升级失败，故使用用户安装位置。
旧全局目录可能仍有残留，不声称完成全局清理；系统 Python 的 `pip check` 返回 0。
没有使用强制退出、析构绕过或忽略退出码的办法。

### 1.2 桌面构建就绪条件

`engineering/python/scripts/build_desktop_runtime.py` 已修改：

- 自动定位 Python 3.12，避免选到 uv 中其他版本而破坏固定依赖兼容性。
- 复制源码时真正过滤 tests、缓存与字节码；旧实现定义了忽略项但未在遍历中执行。
- 清理前验证运行时、后端、Python 来源和显式依赖来源不重叠；拒绝输出链接逃逸。
- 删除范围限定于指定运行时根的子目录；失败不再被静默吞掉。
- 开始重建即移除旧 runtime.json，避免中断后残留“成功”标记。
- 新增桌面依赖约束文件，固定 CPU torch 2.7.1 与 CasADi 3.8.1。
- 就绪探测实际导入 FastAPI、uvicorn、pydantic、ezdxf、CadQuery、ONNX Runtime、torch、sentence-transformers、ChromaDB；执行 CAD 体积及 torch/NumPy 转换。
- 正常退出、完整报告、有限体积数值和 Python 3.12 均满足才写成功标记，保存依赖清单摘要；明确 UTF-8 子进程输出，避免中文 Windows 解码错误遮蔽原始失败。

这些保护有 24 个针对性测试，覆盖原生退出异常、空/损坏报告、NaN/Inf、错误版本、路径越界、来源重叠、复制过滤及成功标记生命周期。

实际桌面 Python 3.12.14 已补装 177 个依赖，`pip check` 退出 0。
九个关键模块的真实导入、CAD 盒体体积 6、torch/NumPy 转换及进程退出均通过。
实际版本为 CadQuery 2.5.2、CasADi 3.8.1、NumPy 2.2.6、torch 2.7.1+cpu、ChromaDB 1.0.0。
首次完整探测超时 180 秒，保留 `desktop-first-cold-start.json`；随后重跑通过，
其中 sentence-transformers 导入约 51.5 秒、torch 约 13.3 秒、ChromaDB 约 14 秒。
首次冷启动偏慢仍是体验风险；不能因重跑通过就删除首次超时记录。

用桌面自带 Python 启动真实 start_server.py，使用随机本机端口和临时 SQLite 数据库：
`/api/health/ping` 返回 200/ping=true，`/api/health` 返回 200/status=ok/database=ok，
未登录访问 `/openapi.json` 返回预期的 401。探测完成后停止自建进程。
这是启动与健康/鉴权边界检查，不是已认证业务端点、桌面 UI 或整条加工链路验收。
未重新构建安装包，也没有仅凭依赖修复写入桌面打包成功标记。

已将 `.wslconfig` 恢复原 6GB 配置，原备份保留在 `D:/nexent-deploy/wslconfig-before-i8-20261016.txt`。
随后定向终止 docker-desktop 发行版并重启 Desktop，问题仍复现；未重置 Docker、删除卷或清理 Nexent 数据。
发行版内部诊断也发生超时，当前证据不足以确认是内存不足、网络路由还是引擎内部故障。
已停止本轮临时启动的 Docker Desktop，保留原容器、卷和数据。

因此 N01—N06 仍保留待在线验收状态，其中 N04 已具备本地技能来源与包。没有把容器启动瞬间当作稳定运行，没有宣称完成 Skill 导入、知识库全量灌入或 Nexent 实际多跳调用。
