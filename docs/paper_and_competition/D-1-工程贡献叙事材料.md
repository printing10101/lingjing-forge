## 2. P2-1 工程贡献：PyCAM 后端真实可用

### 2.1 问题背景

ADR-018 阶段 7 的 `CamAdapter` 原有 5 个子后端中，`internal_only` 仅完成 AABB 包围盒级快速预筛（明确标注「不可替代 CAM 软件二次校验」），`nx_open` / `powermill` 依赖商业许可证，`manual` 为兜底。即软件链路在 `internal_only` 模式下未真正调用任何 CAM 软件，`cam_report.json` 的 `cam_software_report` 字段缺乏真实 CAM 软件校验结论。

P2-1 的目标是让至少一套真实 CAM 软件可用，使 `cam_report.json` 携带真实 CAM 软件校验结论，为车间落地提供可信输入。

### 2.2 PyCAM 选型理由

选择 PyCAM 作为 P2-1 首选的真实 CAM 软件后端，理由：

1. **开源免费**：无授权门槛，独立项目可负担（NX / PowerMill 需导师实验室资源）
2. **Python 原生**：与现有 FastAPI 后端无缝集成，subprocess 调用链简单
3. **G 代码相关**：与 G 代码生成模块同语言生态，便于包装器脚本开发
4. **降级路径清晰**：PyCAM 不可用时仍可降级到 `manual` 模式，链路不中断

### 2.3 PyCAM 0.6.x 真实能力调研结论

P2-1 实施过程中对 PyCAM 0.6.4 进行了真实能力调研，结论与 PyCAM 官方文档存在重要偏差，必须在论文中诚实标注：

| 项目 | PyCAM 官方文档表述 | 真实测试结论 |
|------|--------------------|--------------|
| 软件定位 | CNC 刀轨生成与仿真 | **刀轨生成器**（DXF/STL → G 代码），不是完整 G 代码仿真器 |
| G 代码导入 | 「支持 G 代码」 | `Importers/` 仅支持 DXF/STL/SVG/PS，**不支持 G 代码导入** |
| 命令行入口 | `python -m pycam` | 无 `__main__.py`，`python -m pycam` 不可用 |
| 碰撞检测 | 「完整碰撞检测」 | 仅刀轨生成阶段的几何检查，不支持刀柄-工件 / 刀具-夹具碰撞 |

这一调研结论直接影响工程实现：不能直接调用 PyCAM 解析 G 代码，必须在包装器脚本中自实现轻量 G 代码解析器，并在 PyCAM 能力范围内执行基础校验。

### 2.4 包装器脚本设计

为绕开 PyCAM 不支持 G 代码导入的限制，P2-1 实现了包装器脚本 [autorun_gcode_check.py](../../python/scripts/cam_adapters/pycam/autorun_gcode_check.py)，作为 `CamAdapter._PyCamBackend` 与 PyCAM 之间的桥接层。

**调用协议**（与 NX Open 后端对齐）：

```bash
python <pycam_executable> <gcode_file_path> <controller_type>
```

**输出协议**（stdout 单行 JSON）：

```json
{
  "status": "pass" | "fail" | "error",
  "collisions": [
    {
      "collision_type": "workspace_limit" | "safe_z_violation" | "rapid_in_material" | "tool_workpiece",
      "block_number": 42,
      "message": "刀轨在 N42 处超出工作空间 X+ 边界",
      "severity": "critical" | "warning"
    }
  ],
  "messages": ["PyCAM 校验完成", "刀轨总段数: 128"]
}
```

**退出码**：0（status=pass/fail）或 1（status=error，由 `cam_adapter.py` 自动降级到 manual）。

### 2.5 四项基础校验

包装器脚本在 PyCAM 能力范围内实现 4 项基础校验：

1. **工作空间边界检查**（`_check_workspace_limits`）：刀轨点位是否超出机床工作空间 X/Y/Z 行程，severity=critical
2. **安全 Z 检查**（`_check_safe_z`）：G0 快速移动时 Z 是否低于安全平面（默认 50mm），severity=critical
3. **G0 快速移动在材料内部检测**（`_check_rapid_in_material`）：G0 移动时 Z 低于材料顶面阈值（默认 5mm），severity=warning
4. **刀轨连续性检查**（`_check_move_continuity`）：相邻点位距离低于最小阈值（默认 0.001mm），severity=warning

**PyCAM 不支持的检测项**（包装器脚本在 `messages` 中明确标注）：
- 刀柄-工件碰撞（toolholder_workpiece）
- 刀具-夹具碰撞（tool_fixture）
- 完整的材料切除仿真
- 机床运动学仿真（5 轴、多轴）

这些限制要求工程师结合 `manual` 校验清单或 NX Open / PowerMill 后端补充检测。

### 2.6 配置字段重命名

P2-1 实施过程中发现原配置字段 `pycam_python_module` 与 PyCAM 真实能力不符（PyCAM 无 `__main__.py`，不能作为 Python 模块直接调用）。重命名为 `pycam_executable`，环境变量 `LNN_CAM_PYCAM_EXECUTABLE` 指向包装器脚本路径。

这一重命名体现了工程诚实性：不假装 PyCAM 可作为模块调用，明确指向自实现的包装器脚本。

### 2.7 测试矩阵（4/4 通过）

P2-1 测试矩阵覆盖真实脚本调用与降级场景：

| 用例 | 场景 | 期望 | 结果 |
|------|------|------|------|
| T1 | 真实包装器脚本调用（PyCAM 已安装） | `backend_used="pycam"`，`degraded=False` | PASS |
| T2 | `pycam_executable` 为空（未配置） | 降级到 manual，`degraded=True`，`degradation_reason` 非空 | PASS |
| T3 | 包装器脚本文件不存在 | 降级到 manual，`degraded=True`，`degradation_reason` 含「文件不存在」 | PASS |
| T4 | `list_available_backends` 返回 5 个后端，pycam 可用性正确反映脚本存在性 | pycam `available=True` | PASS |

**测试结论**：4/4 ALL PASS，PyCAM 后端真实可用，降级链路完整。

## 3. P2-4 工程贡献：CAM 后端降级链路完整

### 3.1 问题背景

P2-1 完成 PyCAM 后端真实可用后，仍存在工程问题：当 NX / PowerMill / PyCAM 均不可用时（如独立开发环境、许可证过期、脚本路径错误），系统应如何响应？

ADR-018 原设计已包含 `manual` 兜底后端，但缺乏系统性验证。P2-4 的目标是验证五层降级链路在所有外部 CAM 软件不可用场景下仍能完整运转，且 `manual_checklist_path` 生成的校验清单文档完整可用。

### 3.2 五层降级策略

`CamAdapter` 实现五层降级策略，按优先级从高到低：

```
internal_only（始终可用，秒级反馈）
    ↓ 用户请求 pycam / nx_open / powermill 但不可用时
pycam（开源，需包装器脚本存在）
    ↓ 包装器脚本未配置 / 不存在 / subprocess 失败 / JSON 解析失败 / status=error
nx_open（需许可证 + NX Open Python 环境）
    ↓ 脚本未配置 / 不存在 / subprocess 失败 / JSON 解析失败 / status=error
powermill（需许可证 + PowerMill 宏文件）
    ↓ 可执行文件未配置 / 不存在 / subprocess 失败 / JSON 解析失败 / status=error
manual（兜底，永不失败，生成 markdown 校验清单）
```

**降级硬约束**（项目记忆）：
- 链路永不中断，所有后端失败时降级到 `manual`
- `manual` 后端生成 markdown 校验清单，等待工程师在前端回填结果
- 降级不抛错，通过 `CamSoftwareReport.degraded=True` + `degradation_reason` 非空表达
- 告知文本必须明确标注「实际使用的 CAM 后端」与「降级原因」

### 3.3 降级触发条件

每个非 `manual` 后端的降级触发条件统一为 5 类：

1. **配置缺失**：`*_executable` 为空
2. **文件不存在**：脚本 / 可执行文件路径不存在
3. **subprocess 失败**：超时（>600s）/ FileNotFoundError / 其他异常
4. **非零退出码**：subprocess 返回非零，读取 stderr 作为诊断
5. **JSON 解析失败 / status=error**：stdout 非合法 JSON 或 status 不在 {pass, fail} 集合

任一条件触发即调用 `_degrade_to_manual(reason)`，返回 `status="manual_pending"` 的 `CamSoftwareReport`。

### 3.4 manual 后端校验清单

`_ManualBackend` 生成 markdown 校验清单，包含 6 项必查字段（P2-4 验证文件大小 1075 字节，含完整 6 项）：

**必查项**（5 项）：
1. 刀柄-工件碰撞
2. 刀具-夹具碰撞
3. 工作空间超限
4. 安全 Z 高度
5. 过切检查

**工业硬门槛告知**（3 项，写入清单尾部）：
- G 代码必须经 CAM 软件二次校验后方可上机
- 物理机床执行需持证操作员 + 导师签字 + 保险
- 本系统绝不直接接口 CNC 控制器，仅生成校验报告 JSON

**推荐查项**（4 项，可选）：切削力仿真 / 机床运动学 / 后处理器语法 / 刀轨光滑性。

### 3.5 测试矩阵（7/7 通过）

P2-4 测试矩阵覆盖单后端降级、全后端不可用、manual 正常路径、checklist 内容完整性：

| 用例 | 场景 | 期望 | 结果 |
|------|------|------|------|
| T1 | 单后端未配置降级（pycam_executable 为空） | `degraded=True`，`backend_used="manual"` | PASS |
| T2 | 单后端未配置降级（nx_open_executable 为空） | `degraded=True`，`backend_used="manual"` | PASS |
| T3 | 单后端未配置降级（powermill_executable 为空） | `degraded=True`，`backend_used="manual"` | PASS |
| T4 | 全后端不存在路径降级（所有 executable 指向不存在文件） | `degraded=True`，`manual_checklist_path` 文件存在 | PASS |
| T5 | manual 正常路径（cam_backend="manual" 直接调用） | `degraded=False`，`status="manual_pending"`，`manual_checklist_path` 文件存在 | PASS |
| T6 | checklist 内容完整性（含 6 项必查字段 + 工业硬门槛告知） | checklist 文件大小 ≥ 1000 字节，含全部 6 项必查字段 | PASS（1075 字节） |
| T7 | `list_available_backends` 全不可用（所有 executable 为空） | 5 个后端中仅 internal_only 与 manual `available=True`，其余 3 个 `available=False` | PASS |

**测试结论**：7/7 ALL PASS，五层降级链路完整，`manual_checklist_path` 文档完整。

## 4. 工程贡献的论文价值

### 4.1 可复现性

P2-1 / P2-4 的工程贡献具备完整可复现性：

- **包装器脚本开源**：[autorun_gcode_check.py](../../python/scripts/cam_adapters/pycam/autorun_gcode_check.py) 共 764 行，含完整 G 代码解析器与 4 项校验逻辑，无外部黑盒依赖
- **subprocess + JSON 解耦协议**：所有 CAM 软件调用通过 subprocess + stdout JSON 协议，NX Open / PowerMill SDK 升级不破坏 `cam_validation` 模块
- **测试矩阵可重跑**：P2-1 4/4 + P2-4 7/7 测试用例均为自动化脚本，可一键重跑验证
- **配置字段语义清晰**：`pycam_executable` 明确指向包装器脚本，不假装 PyCAM 可作为模块调用

论文「系统实现」章节可引用上述可复现性证据，增强工程贡献的可信度。

### 4.2 工业可用性

五层降级链路的设计体现了工业可用性：

- **永不失败硬约束**：所有外部 CAM 软件不可用时降级到 `manual`，链路不中断
- **诚实能力边界标注**：PyCAM 4 项基础检查的限制在 `messages` 中明确告知，工程师知道何时需要补充 NX Open / PowerMill 检测
- **human-in-the-loop 对齐**：`manual` 后端生成校验清单，工程师在前端回填结果，符合「工程师助手」定位（项目记忆硬约束）
- **合规对齐**：`manual_checklist_path` 包含工业硬门槛告知（持证操作员 + 导师签字 + 保险），不跳过合规流程

论文「工程验证」章节可强调：本系统不是「全自动生产线」，而是「车间可用工程师助手」，五层降级链路是这一立场的技术支撑。

### 4.3 诚实标注

P2-1 对 PyCAM 0.6.x 真实能力的调研结论与官方文档存在重要偏差，本材料第 2.3 节已诚实记录。论文写作中应保留这一诚实标注，避免夸大 PyCAM 的能力。

具体诚实标注点：
- PyCAM 是刀轨生成器，不是完整 G 代码仿真器
- PyCAM `Importers/` 不支持 G 代码导入
- PyCAM 无 `__main__.py`，`python -m pycam` 不可用
- 包装器脚本自实现轻量 G 代码解析器，非调用 PyCAM 原生功能
- 4 项基础校验是 PyCAM 能力范围内的检查，不替代 NX Open / PowerMill 的完整碰撞检测

这一诚实标注是学术诚信的体现，也是工程贡献可被同行复现的前提。

### 4.4 合规对齐

P2-1 / P2-4 的工程贡献与项目记忆中的合规硬约束完全对齐：

- **`cam_validation_required` 始终 True**：CAM 校验不可跳过
- **`allow_delete_succeeded` 始终 False**：SUCCEEDED 状态禁删，避免阶段 5 任务悬空
- **系统绝不直接接口 CNC 控制器**：CAM 软件调用通过 subprocess，阶段 7 产物终止于 `cam_report.json`
- **物理机床执行由持证操作员 + 导师签字 + 保险流程独立推进**：阶段 7 不触及物理机床

论文「讨论」章节可强调：本系统的工程贡献不仅在于技术实现，更在于合规框架的设计——五层降级链路 + human-in-the-loop + 工业硬门槛告知共同构成「合规可上机」的工程基础。

## 5. 工程贡献的局限

### 5.1 PyCAM 能力局限

P2-1 实现的 PyCAM 后端仅完成 4 项基础校验，不检测：
- 刀柄-工件碰撞
- 刀具-夹具碰撞
- 完整的材料切除仿真
- 机床运动学仿真（5 轴、多轴）

这些检测项需 NX Open / PowerMill 后端补充（P2-2 / P2-3，依赖导师实验室资源，待执行）。

### 5.2 降级链路的工程代价

五层降级链路在所有外部 CAM 软件不可用时降级到 `manual`，但 `manual` 后端依赖工程师手动回填，存在工程代价：
- 工程师需在 NX / PowerMill / PyCAM 中手动加载 G 代码并按清单逐项校验
- 回填结果的质量依赖工程师经验
- 不适合高并发场景（每个 manual 任务需人工介入）

论文应诚实标注：`manual` 后端是合规兜底，不是高效生产路径。

### 5.3 未触及物理机床

P2-1 / P2-4 的工程贡献止步于 `cam_report.json`，未触及物理机床执行。物理机床执行需 P3-1 ~ P3-5 全流程（持证操作员 + 导师签字 + 保险 + 试切件质量检测 + 合规归档），属大一独立项目无法独立完成的环节（项目记忆硬约束）。

论文应明确：本系统的工程贡献是「软件链路到 CAM 软件二次校验」的完整落地，物理机床执行是未来工作。
