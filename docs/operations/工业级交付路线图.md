## 1. 代码签名（P0，工业部署硬门槛）

### 1.1 为什么必须做
未签名安装包触发 Windows SmartScreen 红色警告，企业组策略/EDR 可能直接拦截；
macOS 未 notarization 无法静默分发。这是企业是否愿意部署的第一道关卡。

### 1.2 Windows EV 代码签名
1. 采购 **EV（Extended Validation）代码签名证书**（DigiCert/Sectigo/GlobalSign），约 $300-500/年。
   普通 OV 证书会累积 SmartScreen 信誉，EV 可立即消除警告。
2. 证书交付为 USB 硬件令牌（Safenet 等），CI 需用 `signtool` + token 或导出为 pfx（存 GitHub Secrets）。
3. 在 Tauri 配置 `engineering/src-tauri/tauri.conf.json` 增加 Windows 签名：
   ```json
   "bundle": { "windows": { "signCommand": "signtool sign /f cert.pfx /p %CERT_PASSWORD% /fd SHA256 /tr http://timestamp.digicert.com /td SHA256 %1" } }
   ```
4. 证书密码/路径通过 CI Secret 注入（`WINDOWS_CERT_PFX` / `WINDOWS_CERT_PASSWORD`），
   **严禁提交到仓库**（TruffleHog secret-scan 会拦截）。
5. 验收：`Get-AuthenticodeSignature lingjing_2.7.0_x64-setup.exe` 显示 `Valid` + 发行者为团队主体。

### 1.3 macOS 签名 + notarization
1. 申请 Apple Developer Program（$99/年），创建 `Developer ID Application` 证书。
2. `tauri.conf.json`：`"macOS": { "signingIdentity": "Developer ID Application: <Team>" }`。
3. notarization 需 `APPLE_ID` / `APPLE_APP_SPECIFIC_PASSWORD` / `APPLE_TEAM_ID` 三个 Secret，
   Tauri 2 的 `tauri-action` 或 `tauri build` 内置 notarization 流程自动处理。
4. 验收：`spctl -a -vv lingjing.app` 返回 `accepted`。

## 2. 自动更新（P1）

### 2.1 方案：tauri-plugin-updater + 签名更新包
1. 加入依赖（`engineering/src-tauri/Cargo.toml`）：
   ```toml
   tauri-plugin-updater = "2"
   tauri-plugin-process = "2"
   ```
2. 生成签名密钥对（**私钥严禁入库**，存 Secret）：
   ```bash
   npx tauri signer generate --password "$TAURI_UPDATER_PASSWORD"
   # 输出 <PUBKEY> 与私钥文件
   ```
3. `tauri.conf.json` 增加：
   ```json
   "plugins": { "updater": { "pubkey": "<PUBKEY>", "endpoints": ["https://updates.example.com/releases/{{target}}/{{arch}}/{{current_version}}"] } }
   "bundle": { "createUpdaterArtifacts": true }
   ```
4. 更新服务端：托管 `latest.json`（含版本、签名、下载 URL、SHA256）。
   可直接复用 GitHub Releases：`https://github.com/<org>/<repo>/releases/latest/download/latest.json`。
5. 前端调用检查更新（`engineering/src/stores/` 新增 updater store，或直接 `@tauri-apps/plugin-updater`）。
6. 验收：安装 2.7.0 → 发布 2.7.1 更新包 → 应用内提示升级 → 静默下载并重启完成。

### 2.2 未接入 updater 前的过渡方案
在「设置 → 关于」增加「检查更新」按钮，调用 `GET /api/v1/system/version` 对比远端 `VERSION`，
跳转 GitHub Releases 页面手动下载。成本最低，先于 updater 上线。

> **已落地（2026-08-14）**：
> - 后端新增 `GET /api/v1/system/update-check`：对比当前 VERSION 与 GitHub Releases latest tag
>   （语义化版本比较），网络失败 fail-soft（error 短代码 network/parse，不阻断页面）。
>   - 实现：`engineering/python/app/services/update_check.py`
>   - 可配置：`LINGJING_UPDATE_REPO` 环境变量（默认 printing10101/Virtual-Realm-Manufacturing）
> - 前端「关于」页（`engineering/src/views/About.vue`）：
>   - 挂载时经 `/api/v1/system/version` 显示当前版本（替代原静态版本号）
>   - 「检查更新」按钮 → 有更新显示「前往下载」（经 Tauri 原生命令 `open_external_url`
>     打开 GitHub Releases，Web 模式回退 window.open）；已最新/失败均有对应提示
> - 测试：后端 `tests/api/test_update_check.py`（13 用例），前端 `views/__tests__/About.test.ts`（6 用例）；
>   eslint / ruff / cargo check 全绿。

## 3. CSP 收紧（P2）

### 3.1 现状
`engineering/src-tauri/tauri.conf.json` 的 `security.csp` 为：
`script-src 'self' 'unsafe-inline' 'unsafe-eval'`。
`unsafe-eval` 是 52a581b 为修复白屏而加入（前端源码本身无 `eval`，
怀疑来自 Three.js 着色器 `new Function` 或 Vite 构建产物）。

### 3.2 安全迁移步骤（逐步验证，每步后 `pnpm tauri:build` 实测白屏是否复现）
1. 先移除 `'unsafe-eval'`，保留 `'unsafe-inline'`：构建 + 运行，检查 3D 仿真/着色器是否正常。
2. 若 Three.js 报 `new Function` 被 CSP 拦截：改用预编译着色器（`ShaderMaterial` 用内联 GLSL 字符串，
   避免运行时 `new Function`），或锁定 Three.js 版本到不动态编译着色器的构建。
3. 再移除 `'unsafe-inline'`：需将入口内联脚本改为外链 `bundle.js`，并确认 Tauri `assetProtocol` 下
   `'self'` 覆盖了自定义协议资源。
4. 最终目标 CSP：`default-src 'self' data: blob:; script-src 'self'; style-src 'self' 'unsafe-inline'`
   （`style-src 'unsafe-inline'` 因 Element Plus 内联样式可保留）。
5. 同时将 `withGlobalTauri: true` 改为 `false`，前端改用显式 `import { invoke } from '@tauri-apps/api'`。

### 3.3 验收
`pnpm tauri:build` 产物运行无白屏、无控制台 CSP violation、3D 仿真/着色器正常。

## 4. CAM 软件二次校验联调（P1）

### 4.1 现状
`cam_validation` 默认 `internal_only`（AABB 秒级预筛）。`nx_open`/`powermill` 后端为代码路径，
**尚无真实 NX/PowerMill 联调记录**。这是「G 代码能否上机床」的关键未验证环节。

### 4.2 联调验证计划
1. 准备一台已授权 NX（含 NX Open）或 PowerMill 的车间工作站。
2. 配置 `LNN_CAM_DEFAULT_BACKEND=nx_open`（或 `powermill`）+ 对应 executable 路径。
3. 用 `data/outputs/e2e_v2/` 的 20 个基准 case × 至少 3 种控制器，跑通二次校验，
   对比 `cam_report.json` 与人工校验结论的一致性。
4. 记录三类缺陷：漏报（G 代码错误未检出）、误报（合法 G 代码被判错）、崩溃（subprocess 协议）。
5. 验收标准：漏报率 0（安全关键）、误报率 < 10%（否则工程师失去信任）、协议超时正常降级 manual。
6. 文档沉淀到 `docs/integrations/`（新文件），并补一条 ADR。

### 4.3 安全边界（项目硬约束，勿破坏）
- 系统定位「工程师助手」，产物终止于 CAM 校验报告 JSON；
- **绝不直接接口 CNC 控制器**，物理执行需持证操作员 + 导师签字 + 保险；
- `cam_validation_required` 恒 True、`allow_delete_succeeded` 恒 False。

## 5. 安装包体积优化（P2）

### 5.1 现状
约 397MB（内嵌 Python 运行时 + torch CPU ≈476MB，sentence-transformers 硬依赖）。

### 5.2 方案：按硬件档位分档安装包
1. `minimal` 档（CAM 核心 + 云端 API，无本地 LLM/嵌入）：裁剪 torch/sentence-transformers，
   目标 <150MB。
2. `standard` 档（当前默认）：保留 CPU torch，供本地小模型。
3. `high` 档：可选下载 GPU 版 torch（不预装）。
4. 嵌入模型改为首次启动按需下载（复用 `HF_ENDPOINT`/`OLLAMA_MODEL_PATH` 思路），
   减少安装包内静态权重体积。
