## 1. 权限层级划分

系统采用 **四层权限模型**，从底向上权限递增：

```
┌──────────────────────────────────────────────────────┐
│  L4  系统管理员 (System Administrator)              │  最高权限
│      - 全部系统配置、用户管理、审计日志              │
├──────────────────────────────────────────────────────┤
│  L3  安全管理员 (Security Administrator)             │
│      - 角色管理、权限分配、安全策略                  │
├──────────────────────────────────────────────────────┤
│  L2  工艺工程师 / 部门主管 (Engineer / Manager)      │
│      - 项目管理、工艺规划、模板发布                  │
├──────────────────────────────────────────────────────┤
│  L1  操作员 (Operator)                                │  最低权限
│      - 工件导入、仿真查看、NC 代码下载                │
└──────────────────────────────────────────────────────┘
```

### 1.1 资源所有权

- **个人资源**：用户创建的项目、工件、模板默认归属个人，**仅本人 + 管理员**可访问
- **团队资源**：发布到团队/部门后，部门内所有 L2+ 用户可访问
- **公共资源**：发布到公共模板市场后，全公司可访问

### 1.2 权限继承规则

| 资源类型 | 创建者 | 部门内 L2+ | 全公司 L1+ | 管理员 |
|----------|--------|------------|------------|--------|
| 个人未发布 | | | | |
| 团队发布 | | | | |
| 公共发布 | | | | |

## 2. 用户角色管理

### 2.1 内置角色

| 角色代码 | 名称 | 典型用户 | 权限范围 |
|----------|------|----------|----------|
| `sysadmin` | 系统管理员 | IT 运维 | 全部 |
| `secadmin` | 安全管理员 | CISO / 安全工程师 | 角色 + 审计 |
| `engineer` | 工艺工程师 | 工艺部 | 项目 + 工艺 + 模板发布 |
| `manager` | 部门主管 | 车间主任 | 部门内全部数据 + 工艺审批 |
| `operator` | 操作员 | 车间工人 | 工件导入 + 仿真查看 + NC 下载 |
| `auditor` | 审计员 | 合规专员 | 只读全部数据 + 审计日志 |
| `agent` | 智能体服务账号 | 自动化系统 | 自动化任务专用，权限受严格控制 |

### 2.2 自定义角色

系统支持基于 RBAC 模型创建自定义角色，建议遵循：

- **最小权限原则**：仅授予业务必需的权限
- **职责分离原则**：审批与执行不能由同一角色承担
- **角色命名规范**：`<业务域>_<动作>`，如 `production_approve`、`finance_audit`

### 2.3 用户生命周期

```
[注册] → [角色分配] → [激活] → [使用] → [转岗/权限变更] → [离职/禁用]
```

#### 2.3.1 强密码策略

- **最低 12 位**，必须包含大小写字母、数字、特殊字符
- **90 天强制更换**
- **不能与最近 5 次密码相同**
- **连续 5 次错误后锁定 30 分钟**

#### 2.3.2 账号禁用与删除

- 离职时**当日**禁用账号
- 禁用后 30 天后自动删除账号
- 账号删除前会生成**数据所有权转移报告**，由安全管理员审核

## 3. 数据加密机制

### 3.1 传输加密

| 场景 | 加密协议 | 强制要求 |
|------|----------|----------|
| Web 端 ↔ 服务端 | TLS 1.2+（推荐 1.3） | 生产环境**强制** |
| 服务端 ↔ 数据库 | TLS 1.2+ | 生产环境**强制** |
| 服务端 ↔ Redis | TLS 1.2+ 或 SSH 隧道 | 生产环境**强制** |
| 桌面端 ↔ 服务端 | TLS 1.2+ | 生产环境**强制** |
| DNC ↔ 机床 | 物理隔离网络 / VPN | 推荐 |

### 3.2 存储加密

| 数据类型 | 加密方式 | 密钥管理 |
|----------|----------|----------|
| 用户密码 | bcrypt（cost=12） | 不可逆 |
| JWT 签名密钥 | HS256 + 256-bit 随机密钥 | 环境变量 + K8s Secret |
| 数据库字段级 | AES-256-GCM | KMS 托管 |
| 文件存储 | AES-256-XTS | 静态加密 |
| 备份 | AES-256-GCM | 独立密钥 |

### 3.3 密钥管理

- **开发环境**：使用 `.env` 文件（**严禁**提交到 Git）
- **测试环境**：使用 Vault / AWS KMS
- **生产环境**：**强制**使用 HSM 或云 KMS

### 3.4 TLS 证书

- **推荐**：使用 Let's Encrypt 自动续期
- **企业内网**：使用企业内部 CA
- **过期前 30 天**自动告警
- 禁止使用自签名证书（开发环境除外）

## 4. 敏感信息保护

### 4.1 敏感数据分类

| 等级 | 数据类型 | 示例 |
|------|----------|------|
| **S4 绝密** | 系统主密钥、数据库主密码 | KMS 主密钥 |
| **S3 机密** | 用户密码、API 密钥、NC 代码（涉密工艺） | bcrypt hash、API token |
| **S2 秘密** | 工艺参数、刀具寿命、客户信息 | 工艺路线、客户名 |
| **S1 内部** | 工件几何、用户操作日志 | STEP 文件、操作日志 |
| **S0 公开** | 系统版本、文档 | API 文档、版本号 |

### 4.2 敏感信息处理规范

- **日志脱敏**：禁止在日志中输出完整密码、token、身份证号
- **错误信息**：禁止泄露内部错误细节给前端（参见 `app/core/safe_errors.py`）
- **数据传输**：禁止通过未加密通道传输 S3+ 等级数据
- **数据展示**：UI 中默认脱敏显示（如 `138****1234`）
- **数据导出**：导出 S2+ 等级数据时需要二次确认

### 4.3 个人隐私合规

- **GDPR / 个保法**：用户拥有**数据访问、更正、删除、可携带**四项权利（参见 [用户主权功能详解](./功能详解.md#9-用户主权)）
- **数据保留期限**：
  - 操作日志：365 天
  - 项目数据：用户删除后立即清除
  - 审计日志：≥ 5 年（合规要求）
- **数据出境**：S2+ 等级数据严禁未经审批出境

## 5. 安全操作规范

### 5.1 日常使用规范

#### 5.1.1 账号安全

- **必须**：使用专属账号，不与他人共享
- **必须**：启用多因素认证（MFA），推荐 FIDO2 安全密钥
- **禁止**：在公共电脑保存密码
- **禁止**：使用简单密码（生日、连续数字）

#### 5.1.2 终端安全

- **必须**：离开座位时**锁屏**（`Win + L` / `Ctrl + Cmd + Q`）
- **必须**：使用 HTTPS / SSH 访问服务
- **禁止**：在浏览器保存敏感 token
- **禁止**：在 U 盘等移动介质上长期保存工艺数据

#### 5.1.3 文件处理

- **必须**：外来文件（邮件、U 盘）先杀毒再打开
- **必须**：NC 代码传输前进行 SHA-256 校验
- **禁止**：直接打开陌生人发来的 `.step` / `.exe` 文件

### 5.2 系统管理员额外规范

#### 5.2.1 部署安全

- **必须**：使用官方 Docker 镜像或源码构建
- **必须**：定期 `pip-audit` 扫描依赖漏洞
- **必须**：每月运行 `./health_check.ps1` 检查系统健康度
- **禁止**：以 root 身份运行服务
- **禁止**：将数据库端口暴露到公网

#### 5.2.2 配置管理

- **必须**：`.env` 文件权限 `chmod 600`
- **必须**：定期轮换 JWT 密钥（建议 90 天）
- **必须**：生产环境关闭 debug 模式
- **禁止**：在生产环境使用默认密码
- **禁止**：将密钥硬编码到代码

#### 5.2.3 备份与恢复

- **必须**：遵循 3-2-1 备份策略（3 份副本，2 种介质，1 份异地）
- **必须**：每月进行**恢复演练**
- **必须**：备份数据**加密**且**异地**存储
- **禁止**：备份数据与生产系统同账号访问

### 5.3 开发人员额外规范

参见 [开发文档 - 贡献指南](../development/贡献指南.md) 中的"安全编码"章节。

## 6. 审计与合规

### 6.1 审计日志

系统记录以下事件（不可删除，保留 365 天）：

| 事件类型 | 记录内容 |
|----------|----------|
| 登录 | 用户名、IP、UA、时间、结果 |
| 权限变更 | 操作者、被操作者、变更内容 |
| 数据访问 | 用户、对象类型、对象 ID、动作 |
| 数据修改 | 变更前/后内容（敏感字段脱敏） |
| 敏感操作 | 导出、删除、批量操作 |
| 系统事件 | 启动、停止、配置变更 |

### 6.2 合规支持

- **等保 2.0 三级**：支持（需部署满足相关要求）
- **ISO 27001**：支持（提供合规证据）
- **GDPR / 个保法**：支持（提供数据主体权利工具）
- **SOC 2 Type II**：审计跟踪完整

### 6.3 日志查看

```bash
# 审计员查看审计日志
python -m app.cli audit --action login --user admin --from 2024-01-01

# 导出审计报告
python -m app.cli export-audit --from 2024-01-01 --to 2024-12-31 --output audit-2024.csv
```

## 7. 安全事件响应

### 7.1 事件分级

| 级别 | 描述 | 响应时间 |
|------|------|----------|
| **P0 紧急** | 数据泄露、勒索软件、APT 攻击 | 1 小时内 |
| **P1 高危** | 越权访问、关键服务中断 | 4 小时内 |
| **P2 中危** | 一般漏洞、弱口令 | 24 小时内 |
| **P3 低危** | 扫描告警、可疑行为 | 72 小时内 |

### 7.2 响应流程

```
[事件发现] → [初步评估] → [遏制] → [根除] → [恢复] → [复盘]
```

#### 7.2.1 应急联系

| 角色 | 联系方式 |
|------|----------|
| 安全值班 | security-oncall@lingjing-mfg.com |
| 系统管理员 | sysadmin@lingjing-mfg.com |
| 高管热线 | ciso@lingjing-mfg.com |
| 监管上报 | compliance@lingjing-mfg.com |

#### 7.2.2 数据泄露应急

1. **立即**禁用涉事账号
2. **立即**撤销所有活跃 token
3. **24 小时内**启动内部调查
4. **72 小时内**评估影响范围
5. **按法规要求**向监管机构与用户上报
